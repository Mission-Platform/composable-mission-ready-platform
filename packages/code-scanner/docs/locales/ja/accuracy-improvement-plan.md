## 1. 核となる構造的問題: パイプラインが wasm↔JS 境界を 2 回越えた

フェーズ 1 の前の単一スキャンは次のとおりでした。

```
image (JS)
  → wasm code-scan.scan()            [Rust: binarise + locate + sample]
  → tagged module buffer (JS)        [cross back into JS]
  → decodeQr / decodeMatrix / decodeBarcode (JS façades)
  → wasm qr/matrix/barcode-decode    [cross into a *different* wasm module]
  → payload string (JS)
```

見つかったすべてのシンボルは wasm からコピーされ、JS で再形成された後、2 番目の wasm インスタンスにコピーされてデコードされます。これは
この問題が引き起こすラウンドトリップ。これはパフォーマンスと、この計画にとってさらに重要なことである**精度**の両方に悪影響を及ぼします。
ロケーターとデコーダーは連携できません。

- **ロケーターへのデコード フィードバックはありません。** Rust ロケーターは _single_ にコミットします。
  二値化、シンボル サイズ、モジュール グリッド。サンプリングされたグリッドが JS デコーダのリードソロモン/チェックサムに失敗した場合、次のような問題が発生します。
  異なるしきい値、±1 モジュール サイズ、またはシフトされた原点で再サンプリングするようにロケーターに要求する方法はありません。というコード
  _場所はありますが、デコードできません_ (デバッグログの対象となる正確なケース)
  単に失われただけです。
- **損失のあるハンドオフ。** ロケーターは豊富な中間状態 (グレー レベル、候補ファインダーの中心、モジュールごと) を平坦化します。
  信頼度)、デコーダが認識する前に、ハード `0/1` ビットまでダウンします。デコーダはビットのみから動作します。
- **シンボルの優先順位は鈍い手段です。** 1D コードの場合、JS 側は固定された順序でシンボルを試みます。
  最初に読み取ったものを返します。 UPC-A は先行ゼロ EAN-13 のモジュール レベルのサブセットであるため、UPC-A シンボルは次のようになります。
  EAN-13 として報告されます (新しいテスト スイートで検証済み)。 Rust でデコードすると、ロケーターに構造上のヒント (要素
  カウント、ガード パターン) を使用して、適切なシンボルを選択します。

### ターゲット アーキテクチャ — 1 回の FWS 呼び出し、イメージ入力、ペイロード出力

> **ステータス: 実装されました。** スキャナは `scan_and_decode` をエクスポートし、
> デコーダ FWS グラフを直接デコードし、JS ファサードはその 1 つを介してデコードします
> 電話してください。以下の詳細は、移行の理論的根拠を記録したものです。

```
image (JS)
  → FWS scanner.scan_and_decode()      [binarise + locate + sample + decode]
  → ScanOutcome { format, value } (JS)
```

`scan_and_decode(width, height, luma) -> Option<ScanOutcome>` は `src/fws/scanner.fws` 内でパイプライン全体を実行し、
**デコードされたペイロード**を直接返します (シンボルが見つかってもデコードできない場合、`value` は空です)。 JSのファサード
(`scanner/index.ts`) は、ビルド時に QR、マトリックス、およびバーコード FWS ソースをリンクする薄いマーシャリング レイヤーです。
これらのパッケージは引き続き独立して公開できます。

#### なぜこれが今対処可能なのか

デコーダ クレートはすでにプレーン Rust コアを公開しており、`crates/code-scan`
**ネイティブ テスト用にすでにリンクされています** (`tests/pipeline.rs` は呼び出します)
`mission_platform_barcode_decode::decode_modules`、
`mission_platform_matrix_code_decode::decode` など)。彼らが閉じ込められる唯一の理由は、
`[target.'cfg(not(target_arch = "wasm32"))'.dev-dependencies]` は、各デコーダー クレートが
`#[wasm_bindgen] pub fn decode`、およびそれらのいくつかを 1 つの cdylib にリンクすると、エクスポートされた `decode` で衝突します。
シンボル。

修正は小規模な機械的なリファクタリングでした。**これで 4 つの手順がすべて完了しました**。

1. **すべてのデコーダには、`#[wasm_bindgen]` ではないプレーンな Rust エントリ ポイント**があります。
   (`decode_modules`、`decode_matrix`、`decode_qr`)、および `#[wasm_bindgen]`
   `decode`/`start` エクスポートは、新しい `wasm-api` クレート機能 (デフォルトでオン、`console` によって暗示される) の背後でゲートされます。
2. **`code-scan` は `default-features = false` のデコーダ クレートに依存します**
   (したがって、`wasm-api` はオフになります)、開発依存関係から実際の依存関係に昇格します。 wasm-bindgen `decode` シンボルはありません
   スキャナー cdylib にコンパイルされているため、クラッシュはありません。スキャナー wasm を再構築することで確認できます。
3. `crates/code-scan/src/lib.rs` 内の **`scan_and_decode`** は、デコーダーのプレーン Rust コアをインプロセスで見つけて呼び出します。
   そして `ScanOutcome { 形式を返します。
デコードできない場合は value }` (a `#[wasm_bindgen]` struct; `value` is `unknown`)。
4. **JS ファサードがスリム化されました**: `decodeTagged` ルーティングと 3 つのデコーダー パッケージのインポートがなくなりました。
   単一の `scan_and_decode` 呼び出しに置き換えられました。

これは、検索とデコードが 1 つのアドレス空間を共有するようになるため、以下のすべての精度向上を可能にするステップです。

## 2. Rustでデコードすると精度が向上します

予想される読み取り速度への影響によって大まかに並べられています。 **項目 1 ～ 3 (フェーズ 2) と項目 4 ～ 7 (フェーズ 3) が完了しました**。それぞれが
以下に注釈を付けます。

1. **ロケーター ↔ デコーダーの再試行ループ。 _(完了 — フェーズ 2.)_** 最初のデコード試行が失敗すると、`scan_and_decode`
   Rustを離れることなく再サンプリングします: 2回目の(適応的)二値化を試行し、サブモジュールの原点をシフトします。
   (`SAMPLE_OFFSETS`)、および消去対応デコーディングとブラインド デコーディングの両方で、シンボルのパスを通過する最初の候補を受け入れます。
   独自のエラー修正。これは、「場所は特定されたがデコードできない」障害を直接攻撃します。
2. **ローカル/適応型二値化。 _(完了 — フェーズ 2。)_** `image::binarize` (グローバル **Otsu**) が高速の最初として維持されます
   試み; `image::binarize_adaptive` は、ウィンドウ化された **ローカル平均 C** しきい値を (積分画像経由で) 追加するため、グレア、
   グラデーションや不均一な照明によって、暗いモジュールが背景にマージされなくなりました。再試行ループでは両方が試行されます。
3. **グレーレベル (サブピクセル) モジュールのサンプリング。 _(完了 — フェーズ 2。)_** `qr` および
   `datamatrix` は `scan_with_confidence` を取得しました。これは、バイリニアを使用して _grey_ イメージからモジュールの中心をサンプリングします。
   補間を行い、ローカルしきい値に近いモジュールに信頼性が低いとしてフラグを立てます。それらはデコーダに渡されます
   (`decode_qr_with_erasures` / `decode_matrix_with_erasures`) リード・ソロモン **消去**として、
   エラーと消去の修正機能 (`gf`、`reed_solomon`)
   未知のエラーを最大 2 倍の割合で修復します。
4. **1D およびデータ マトリックスに対するマルチスケール + 回転の堅牢性。 _(完了 — フェーズ 3.)_** QR ロケーターはすでに
   3 つのファインダーセンターによる回転耐性。データ マトリックスは **任意** の回転で読み取るようになりました: コーナーベースのアフィン
   ロケーター (`scan_oriented_candidates` — 4 つの極端なインク コーナー、solid エッジから検出された L コーナー、
   対角は平行四辺形ルールによって再構成され、サイズはタイミング エッジから読み取られ、独立した方向にサンプリングされます。
   列/行軸なのでせん断も処理されます)
   中程度の角度をカバーし、まっすぐにして再試行するフォールバックにより急な角度を回復します。`Bitmap::orientation` は、
   最小領域の境界ボックス スイープによる回転 (極点のコーナーが縮退する 45° ファミリで堅牢)、
   `image::rotate_luma` はフレームをまっすぐにし、調整された直立パイプラインがそれをサンプリングします。 1次元バーコードは
   同様に - 傾きが回復し、フレームが真っ直ぐになります (4 つの軸を揃えた向きがすべて試行されました)。
   水平走査線はバーを横切ります。さまざまな角度にわたる回転キャプチャ パイプライン テストによってカバーされます (角度を含む)。
   45°/90°/180°+) および強化された JS 分解プロファイル。
5. **1D のシンボルの明確化。 _(完了 — フェーズ 3.)_** UPC-A と先頭ゼロ EAN-13 のあいまいさは次のように解決されます。
   **数値体系の数字**:
   `decode_any_barcode` は、勝利シンボルを後処理します。
   `disambiguate_symbology`、番号体系の数字が次の EAN-13 を報告します。
   `0` を 12 桁の UPC-A 形式 (先頭のゼロを取り除いたもの) とし、本物の EAN-13 はそのままにします。 _残り:_ 持ち運び
   より豊富な位置の構造 (ガードバーの位置、要素数) を決定に組み込み、意図したシンボルを公開します。
   そのため、呼び出し側はそれを制限できます。
6. **アステカのサポート。 _(完了 — フェーズ 3。)_** `@mission-platform/matrix-code`
   エンコーダはすでに Aztec を生成していましたが、スキャナには Aztec _locator_ がありませんでした。コンパクトなアステカのブルズアイ ロケーターを追加しました
   (`crates/code-scan/src/aztec.rs`): 9 回の `1:1:1:1:1:1:1:1:1` ファインダー署名によって中央のブルズアイを見つけます。
   (内側の 7 つは信頼済みで実行され、外側の 2 つはモード リングに接触するため存在する必要があるだけです)、両方の軸で検証します。
   モジュール サイズを回復し、スペックル クリーンされたコピー上で妥当な各コンパクト サイズ (15/19/23/27) をサンプリングし、それぞれをルーティングします。
   既存の Aztec デコード パスに接続します。そのモード メッセージ + リードソロモン チェックでは間違ったサイズが拒否されます。 `scan_and_decode`
   `FORMAT_AZTEC` として報告されます。
7. **複数のシンボル + ROI スキャン。 _(完了 — フェーズ 3。)_** `scan_and_decode_all`
   デコードされたすべての個別のシンボルを返します (フレーム全体の粗いから細かいまでのスイープ、重複する半分と象限、
   `(format, value)` によって重複排除されます)、および
   `scan_and_decode_roi` は、**以前の Rust では**呼び出し元が指定した領域をトリミングします
   二値化なので、レティクル クロップは周囲の雑然としたものを前もって拒否します。どちらも JS ファサードに表示されます
   (`scanImageDataAll`、`scanImageData(image, roi)`)。

## 3. 検証戦略

**定量化された次の機会 (特定されていますが、まだ解読されていません):**

- **桁ごとの 1D 行デコード (最大の機会)。** UPC/EAN フォルダーは数百のスキャン ラインを検出しますが、ほとんどデコードします。
  ハード カメラの写真はありません (`upca-2` 206 が検出 / 0 デコード、`upce-2` 160 / 0、`ean13-3` 204 / 6)。根本的な原因
  それは、ロケータがモジュール ビットを
  デコーダ。遠近法で短縮すると、実際のモジュール幅がシンボル全体で変化するため、グローバル グリッドがドリフトします。
  そして、厳格な EAN/UPC セル グリッドはそれを拒否します。修正は、各桁の行に一致する ZXing スタイルの **桁ごと** 行デコーダです。
  グローバルな量子化ではなく、ローカルでのランレングス比 (パターン一致分散) - より大きな変更
  ロケーター↔デコーダー インターフェイス。次のステップ 2 の反復として追跡されます。
- **QR パースペクティブ / アライメント パターン サンプリング。** `qrcode-1` (77 が検出 / 0 デコード) および `qrcode-6` (60 / 0) は
  上位バージョンのシンボル: サンプラーは 3 つのファインダー センターから純粋に**アフィン** グリッドを構築し、それが全体に渡ってドリフトします。
  大きなシンボル、または遠近法が歪んだシンボル。右下の **配置パターン** を使用する
  4 点透視変換 (ZXing の `Detector` のように) の場合、一致する QR が勝ちます。
- **データ マトリックスのサイズ設定 + 極性。** 単一の `inverted` データ マトリックスは極性反転後に配置されますが、
  ロケーターによってサイズが間違っているため (実際のサイズが約 12 ～ 14 である 10 桁の数値シンボルの場合は 22×22)、デコードされません。ある
  フルフレーム極性反転再試行が試作されましたが、コーパススイープ時間が 2 倍になったため、このステップでは元に戻されました。
  ネット コーパスがゼロの場合は勝ちます (ブロッカーは極性ではなく DM サイジングです)。 DM ロケーターが戻ったら、反転サポートが戻るはずです
  サイズ設定が厳格化され、スコープが設定されているため、追加のパスは失敗するフレームでのみ実行されます。
- **アステカ サンプリング。** `aztec-1` (68 が検出 / 0 がデコード): ブルズアイは検出されますが、軸に合わせたグリッド サンプリングは検出されます。
  これらのキャプチャはまだ回復していません。

### ステップ 3 — GS1 DataBar (RSS-14) エンコード + デコード + ロケーター _(RSS-14 完了)_

### ステップ 4 — PDF417 エンコード + デコード + スタック行ロケーター _(完了)_

新しいクレート トリオは、リポジトリの `*-common` / `*-encode` / `*-decode` 分割をミラーリングし、`com.google.zxing.pdf417.*` を移植します。
(Apache-2.0):

- **`pdf417-common`** — 共有テーブルと計算の両側に必要なもの: シンボル ↔ コードワード テーブル (2,787 エントリ、
  ZXing リファレンスから生成)、コードワード/クラスター ルックアップ (`get_codeword`、`bucket_from_symbol`)、
  module-bit-count → シンボル サンプラー (正確な高速パスと遅延構築された最近接比フォールバック)、および **GF (929)
  Reed-Solomon** 誤り訂正デコーダ (`ModulusGF` / `ModulusPoly` / ユークリッド アルゴリズム)。単体テストでは、次のすべてのことをアサートします。
  コードワード値には、3 つのクラスタとラウンドトリップのそれぞれにシンボルがあります。
- **`pdf417-decode`** — GF (929) EC 修正と高レベルのビットストリーム パーサー (`DecodedBitStreamParser`) をカバー
  **テキスト**、**バイト**、**数値**
  圧縮。ロケーターが組み立てたフラット コードワード配列を消費し、ペイロードを返します。
- **`pdf417-encode`** — バイト圧縮エンコーダー (あらゆるバイト ペイロードが正確にラウンドトリップ)、次元サイジング、
  EC コードワード ジェネレーター (9 つの EC レベルすべての `EC_COEFFICIENTS`、リファレンスから生成) およびモジュール マトリックス
  レイアウト (スタート/ストップ ガード、左/右列インジケーター)。コードワード配列 (コードワードレベルの場合) の両方を公開します。
  ラウンドトリップ) とパックされたモジュール ビットマップ (イメージ パス テスト用)。

スキャナーは `crates/code-scan/src/pdf417.rs` を取得しました。 PDF417 は_スタックリニア_です
シンボル体系のため、ロケーターは一度に走査線を処理します。各画像行でスタート ガードを見つけ、17 モジュールを読み取ります。
ストップ ガードまでのコードワード (各 8 バー/スペース ラン)、行から列/行数/EC レベルのメタデータを投票します。
インジケーターは、データ コードワードを `rows × cols` 行列に配置します (スキャン ライン全体にわたるセルごとに多数決で投票されます)。
各バーコード行をカバーし、それを RS チェック デコーダに渡します。 2 番目のパスでは、すべての行を右から左に読み取ります。
180 度回転したシンボルもデコードできます。これは、`FORMAT_PDF417` として `scan_and_decode` に配線されます。

堅牢性に関する 2 つの詳細が不可欠であることが判明しました。

- **ホット パスでの完全一致のみのサンプリング。** 実行ごとのサンプラーは完全一致のみを使用します。
  (`sample_codeword_symbol_exact`);きれいにサンプリングされない実行は、列を保持する `-1` _hole_ になります。
  調整されており、投票ではスキップされます。これにより、すべての画像のすべての行を低コストでスキャンし続けることができます (O (テーブル サイズ))。
  そうしないと、最近接比フォールバックがコーパス スイープを支配することになります。
- **RS の過剰補正に対するホール ガード。** EC レベルが高い場合、リードソロモンは喜んで
  ほとんど空のアセンブリからの_有効だが間違っている_コードワード (ガベージ `"AAAA…"` デコードとして観察される)。したがって、ロケーターは
  ホールの数が `num_ec / 2` (RS 補正バジェット) を超えるとデコードを拒否します。これにより、**ごと** が削除されます。
  すべての正しいものを保持しながらガベージ デコードを行い、ネガティブ フォルダーの誤検知ガードをクリーンに保ちます。

途中で修正されたバグ: ビットストリーム パーサーのデフォルト アームが破損したストリーム上で永遠に回転する可能性がありました (テキストの再実行)
消費できないコードワードでの圧縮);前進がない場合は回避されるようになりました。

**結果:** `pdf417-1` / `pdf417-2` / `pdf417-3` は **0 → 8 / 13 / 8** になりました
回転 0 で正しくデコードされ、180 度でも正しくデコードされました (**58** 回転全体で正しくデコードされました)。その他のデコードでは **回帰はありません**
フォルダーとネガティブ フォルダーの誤検知は依然として **ゼロ** です。往復料金が適用されるのは、
`pdf417-decode/tests/roundtrip.rs` および `code-scan/tests/generated.rs`、および完全なイメージ パス (エンコード → レンダリング →
`scan_and_decode`、含む180°）による
`code-scan/tests/pipeline.rs`。

**次の PDF417 反復:** 回転 **90°/270°** はベースライン 0 に留まります — 4 分の 1 回転したシンボルが垂直バーとして表示されます
行スキャン ロケーターが読み取れないこと。列スキャン (転置) パス、または転置されたフレームに給電するハーネスは、
マッチングのフォローアップ。より急なスキューには、完全な ZXing 4 コーナー `Detector` パースペクティブ モデルが必要になります。
