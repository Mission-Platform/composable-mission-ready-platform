## 1.核心结构问题：管道两次跨越wasm↔JS边界

在第一阶段之前，单次扫描是：

```
image (JS)
  → wasm code-scan.scan()            [Rust: binarise + locate + sample]
  → tagged module buffer (JS)        [cross back into JS]
  → decodeQr / decodeMatrix / decodeBarcode (JS façades)
  → wasm qr/matrix/barcode-decode    [cross into a *different* wasm module]
  → payload string (JS)
```

每个找到的符号都从 wasm 中复制出来，在 JS 中重新整形，然后复制到第二个 wasm 实例中进行解码。这是
问题所涉及的往返行程。它会损害性能，更重要的是，对于该计划来说，**准确性**，因为
定位器和解码器不能合作：

- **没有对定位器的解码反馈。** Rust 定位器提交给_single_
  二值化、符号大小和模块网格。如果采样网格在 JS 解码器中未通过 Reed–Solomon/checksum，则有
  无法要求定位器使用不同的阈值、±1 模块大小或移动的原点重新采样。一个代码
  _已定位但不可解码_（调试日志记录目标的确切情况）
  简直就是迷失了。
- **有损切换。** 定位器展平丰富的中间状态（灰度级、候选查找中心、每个模块
  在解码器看到它之前，置信度）下降到硬 `0/1` 位。然后解码器仅根据位进行工作。
- **符号优先级是一种生硬的工具。** 对于一维代码，JS 端会以固定顺序尝试符号系统，并且
  返回第一个读取的内容。由于 UPC-A 是前导零 EAN-13 的模块级子集，因此 UPC-A 符号是
  报告为 EAN-13（由新测试套件验证）。 Rust 中的解码让定位器携带结构提示（元素
  计数、守卫模式）来选择正确的符号系统。

### 目标架构 — 一次 FWS 调用、图像输入、负载输出

> **状态：已实施。** 扫描仪导出 `scan_and_decode`，链接
> 直接解码 FWS 图，JS 外观通过该单一解码
> 打电话。下面的详细信息记录了迁移的理由。

```
image (JS)
  → FWS scanner.scan_and_decode()      [binarise + locate + sample + decode]
  → ScanOutcome { format, value } (JS)
```

`scan_and_decode(width, height, luma) -> Option<ScanOutcome>` 在 `src/fws/scanner.fws` 内运行整个管道，并且
直接返回**解码后的有效负载**（当符号已定位但无法解码时，`value` 为空）。 JS 外观
(`scanner/index.ts`) 是一个薄编组层，在构建时链接 QR、矩阵和条形码 FWS 源；
这些软件包仍然可以独立发布。

#### 为什么现在这很容易处理

解码器箱已经公开了普通 Rust 核心，并且 `crates/code-scan`
**已经将它们链接到其本机测试**（`tests/pipeline.rs` 调用
`mission_platform_barcode_decode::decode_modules`,
`mission_platform_matrix_code_decode::decode` 等）。他们被限制的唯一原因
`[target.'cfg(not(target_arch = "wasm32"))'.dev-dependencies]` 是每个解码器 crate 导出一个
`#[wasm_bindgen] pub fn decode`，并将其中几个链接到一个 cdylib 会与导出的 `decode` 发生冲突
符号。

修复是一个小的机械重构 - **所有四个步骤现已完成**：

1. **每个解码器都有一个普通 Rust 入口点**，即_不是_ `#[wasm_bindgen]`
   （`decode_modules`、`decode_matrix`、`decode_qr`）和 `#[wasm_bindgen]`
   `decode`/`start` 导出在新的 `wasm-api` 包功能后面进行门控（默认情况下打开，并由 `console` 暗示）。
2. **`code-scan` 取决于包含 `default-features = false` 的解码器包**
   （因此 `wasm-api` 关闭），从开发依赖项提升为真正的依赖项。没有 wasm-bindgen `decode` 符号
   编译到扫描仪 cdylib 中，因此不存在冲突 - 通过重建扫描仪 wasm 进行验证。
3. `crates/code-scan/src/lib.rs` 中的 **`scan_and_decode`** 定位，然后在进程中调用解码器的普通 Rust 核心
   并返回 `ScanOutcome { 格式，
值}` (a `#[wasm_bindgen]` struct; `value` is `undefined`（当不可解码时）。
4. **JS 外观被精简**：`decodeTagged` 路由和三个解码器包的导入消失了，
   替换为单个 `scan_and_decode` 调用。

这是下面每一项精度改进的启用步骤，因为定位和解码现在共享一个地址空间。

## 2. 一旦使用 Rust 进行解码，就会解锁准确性改进

大致按预期读取率影响排序。 **第 1-3 项（第 2 阶段）和第 4-7 项（第 3 阶段）已完成**；每个都是
注释如下。

1. **定位器↔解码器重试循环。 _（完成 — 第 2 阶段。）_** 当第一次解码尝试失败时，`scan_and_decode`
   在不离开 Rust 的情况下重新采样：它尝试第二次（自适应）二值化，子模块原点转移
   (`SAMPLE_OFFSETS`)，以及擦除感知和盲解码，接受通过符号的第一个候选者
   自己纠错。这直接攻击_已定位但不可解码_故障。
2. **本地/自适应二值化。 _（完成 — 第 2 阶段。）_** `image::binarize`（全局 **Otsu**）保持为快速优先
   尝试； `image::binarize_adaptive` 添加了一个窗口**局部平均 C** 阈值（通过积分图像），因此眩光，
   渐变和不均匀的照明不再将深色模块合并到背景中。重试循环会尝试两者。
3. **灰度级（亚像素）模块采样。 _（完成 — 第 2 阶段。）_** `qr` 和
   `datamatrix` 获得 `scan_with_confidence`，它使用双线性从灰色图像中采样模块中心
   插值并将接近局部阈值的模块标记为低置信度。这些被传递到解码器
   （`decode_qr_with_erasures` / `decode_matrix_with_erasures`）作为里德-所罗门 **删除**，其中
   错误和删除校正器（`gf`、`reed_solomon`）
   修复未知错误的速度高达两倍。
4. **一维和数据矩阵的多尺度+旋转鲁棒性。 _（完成 — 第 3 阶段。）_** QR 定位器已经
   通过其三个取景器中心实现旋转容差。 Data Matrix 现在可在 **任意** 旋转处读取：基于角的仿射
   定位器（`scan_oriented_candidates` — 四个极端墨水角，从 solid 边缘检测到的 L 角，
   通过平行四边形规则重建对角，从时序边缘读取大小，沿独立采样
   列/行轴，因此也可以处理剪切）
   覆盖中等角度，拉直并重试回退可恢复陡峭角度：`Bitmap::orientation` 找到
   通过最小面积边界框扫描进行旋转（在 45° 系列中稳健，极值点角退化），
   `image::rotate_luma` 拉直框架，调整后的直立管道对其进行采样。一维条形码的处理
   同样的方式 - 倾斜恢复并且框架伸直（尝试了所有四个轴对齐方向），因此
   水平扫描线穿过条形。通过跨角度（包括角度）的旋转捕获管道测试进行覆盖。
   45°/90°/180°+）和增强的 JS 降解曲线。
5. **1D 的符号消歧。 _（完成 — 第 3 阶段。）_** UPC-A 与前导零 EAN-13 的歧义通过以下方式解决
   **数字系统数字**：
   `decode_any_barcode` 通过后处理获胜符号系统
   `disambiguate_symbology`，报告 EAN-13，其数字系统数字为
   `0` 作为 12 位 UPC-A 形式（去除前导零），同时保持真正的 EAN-13 不变。 _剩余：_携带
   将更丰富的定位结构（防护栏位置、元素计数）纳入决策并公开预期的符号系统
   所以调用者可以限制它。
6. **阿兹特克支持。 _（完成 — 第 3 阶段。）_** `@mission-platform/matrix-code`
   编码器已经产生了 Aztec，但扫描仪没有 Aztec _locator_。添加了紧凑型阿兹特克牛眼定位器
   (`crates/code-scan/src/aztec.rs`)：它通过九轮 `1:1:1:1:1:1:1:1:1` 查找器签名找到中央靶心
   （内部七个运行受信任，外部两个仅需要存在，因为它们接触模式环），在两个轴上验证它，
   恢复模块尺寸，在斑点清洁的副本上对每个合理的紧凑尺寸（15/19/23/27）进行采样，并对每个进行布线
   到现有的 Aztec 解码路径，其模式消息 + Reed-Solomon 检查拒绝错误的大小。 `scan_and_decode`
   将其报告为 `FORMAT_AZTEC`。
7. **多符号+ROI扫描。 _（完成 — 第 3 阶段。）_** `scan_and_decode_all`
   返回每个不同的解码符号（整个帧的从粗到细的扫描，重叠的两半和象限，
   由 `(format, value)` 进行重复数据删除），以及
   `scan_and_decode_roi` 在 Rust 之前**裁剪调用者提供的区域**
   二值化，因此十字线裁剪会预先拒绝周围的杂乱。两者都出现在 JS 外观中
   （`scanImageDataAll`、`scanImageData(image, roi)`）。

## 3. 验证策略

工作的准确性必须通过测量来衡量，而不是通过肉眼来判断。

- **生成图像往返测试。**
  `src/scanner/index.spec.ts` 呈现许多编码器输出 - 五个跨尺寸的 QR 有效负载/UTF-8 加上所有四个 ECC
  级、四个数据矩阵有效负载和七个一维符号（`code128`、`code39`、`ean13`、`ean8`、`upca`、`itf`、
  `codabar`) — 并断言完整的 `render → locate → sample → decode` 路径（现在是单个
  `scan_and_decode` 调用）恢复有效负载。一维案例与扫描仪自身的符号系统优先级进行比较
  （包括 UPC-A/EAN-13 消歧）。
- **所有代码类型编码↔解码往返。** `crates/code-scan/tests/generated.rs`
  编码编码器可以生成的**每种**符号体系 - QR（4 个 ECC 级别）、所有四种矩阵符号体系（数据矩阵
  正方形/长方形、GS1 数据矩阵、Aztec）
  以及所有 15 个 1D 符号（包括 Code 93、GS1-128、UPC-E、ITF-14、MSI、Pharmacode），并断言每个解码
  忠实地（重新编码相等），涵盖扫描仪尚无法_定位_的代码类型。
- **第 2 阶段退化案例。** `image.rs` 单元测试照明梯度上的自适应二值化； `tests/pipeline.rs`
  证明了全局 Otsu-only 路径无法读取的梯度退化 QR 可以通过第 2 阶段自适应恢复 +
  灰度采样管道； RS 板条箱测试超出盲错误容量的错误和删除恢复。
- **按格式捕获的种子退化。** 每个生成的图像都被确定性的 **投影** 扭曲
  变换 — 非均匀方面缩放、旋转、倾斜和独立的每角 x/y/z **变形**（单应性） —
  扫描前加上椒盐噪声。强度按格式进行调整，量化了两个定位器限制
  值得修复（参见§2）：QR 基于探测器的网格仅是仿射的，因此它只能容忍轻微的_各向异性_方面，并且
  较大符号漂移之前的_视角_；数据矩阵定位器只能直立，因此只能承受轻微的倾斜
  旋转/倾斜/变形。
- **降解矩阵。** Rust `tests/pipeline.rs` 已经降解了合成捕获物（小规模、盐和胡椒）
  散斑、静区杂乱、杂乱
  “相机框架”）。将其扩展为参数扫描（缩放×噪声×旋转×模糊）并报告**读取率
  每种格式的百分比**，在 CI 中进行控制，因此更改不能默默地使其回归。
- **实拍语料库。** 收集一组固定的真实照片（现场报告参考448×336低分辨率帧

- **决定论。** 保留所有合成降解种子（现有的 `speckle`
  使用固定的 LCG），因此结果是可重复的。

## 4. 建议的排序

1. **阶段 0 — 测试（完成）。** 扩大了生成图像套件（带有种子方面/旋转/倾斜/变形/噪声
   退化），因此管道在重构之前有一个安全网。
2. **阶段 1 — 将解码整合到 Rust（完成）。** 依赖项/功能重构 + `scan_and_decode` + JS 外观
   瘦身。行为保留；通过往返、管道和新的 `scan_and_decode` 测试进行验证，并通过
   重建扫描仪 wasm。
3. **阶段 2 — 二值化 + 子像素采样 + 重试循环（完成）。** 自适应局部二值化，灰色双线性
   将每个模块的置信度采样作为 Reed-Solomon 擦除馈送到解码器，以及全局→自适应 ×
   `scan_and_decode` 中的擦除/盲 × 原点偏移重试循环 — 最大的读取率获胜，现在定位并
   解码在一个 Rust 调用中进行协作。
4. **第 3 阶段 — 旋转/倾斜、符号消歧、Aztec、多符号（正在进行中）。** 1D 符号系统
   消歧（§2 第 5 项）已落地。剩余：
   数据矩阵/一维旋转倾斜容差（第 4 项）、Aztec 定位器（第 6 项）和多符号 + ROI 扫描（第 7 项）——每个都落在其自己的退化矩阵增量后面。

符号系统文件夹，每个文件夹都有一个 `.txt`
预期值； Apache-2.0，销售于
`crates/code-scan/tests/fixtures/zxing-blackbox/` 及归属）。 ZXing式安全带
(`crates/code-scan/tests/blackbox.rs`) 运行整个本机
`scan_and_decode` 在四个四分之一圈旋转 (0/90/180/270) 处对每个图像进行管道处理，并比较每个图像

`unsupported` 文件夹是反向防护：它们的基线是误报的上限。

### 步骤 1 — 语料库 + 广义加载器 + 线束 _(完成)_

语料库已出售，PNG 阅读器已通用（`tests/support/png.rs`：
调色板颜色类型 3，深度为 1/2/4/8，低深度灰度，RGB (A)，灰色+alpha，加上 90/180/270 旋转助手
匹配 ZXing 语义）与加载器单元测试 (`tests/png_loader.rs`)，并提交基线。

### 第 2 步 — 提高支持格式的读取率_（进行中）_

分类（每个图像/旋转的每个文件夹分类为已解码/错误值/已定位但未解码/
未定位）浮现出清晰的图案：
管道现在**定位几乎所有内容**，但**仅解码干净的捕获**。剩下的失败是
绝大多数是_已定位但未解码_，而不是_未定位_。

**完成这一步：**

- **ITF 误报防护。** Interleaved-2-of-5 没有校验位和简单的开始/停止，因此扫描线交叉
  不相关的符号（QR、其他条形）被简单地“解码”为虚假的 2 或 4 位数字值。现在 `itf::decode`
  拒绝短于**六位数**的有效负载，匹配 ZXing 的 `ITFReader::DEFAULT_ALLOWED_LENGTHS` 的下限
  （`{6,8,10,12,14}`）。这导致 `falsepositives`、`falsepositives-2` 和 `unsupported` 中的误报达到
  **零**，并且通过删除那些短路优先顺序的短读取，提升了一些积极的
  文件夹（例如 `qrcode-4`、`qrcode-5`）。由新的回归测试覆盖（`barcode-decode`：
  `itf_rejects_runs_shorter_than_six_digits`）和基线更新。

**量化的下一个机会（已定位，尚未解码）：**

- **1D 每位数行解码（最大的机会）。** UPC/EAN 文件夹定位数百条扫描线，但几乎解码
  没有硬相机照片（`upca-2` 206 位于 / 0 解码，`upce-2` 160 / 0，`ean13-3` 204 / 6）。根本原因
  是定位器将每个扫描线量化为**单个全局模块单元**，然后再将模块位传递给
  解码器；在透视缩短下，真实模块宽度在符号中变化，因此全局网格发生漂移
  严格的 EAN/UPC 单元网格会拒绝它。修复方法是使用 ZXing 风格的 **每数字** 行解码器来匹配每个数字的
  局部游程比（模式匹配方差）而不是全局量化——对
  locator↔decoder 接口，作为下一个 Step-2 迭代进行跟踪。
- **QR 透视/对齐模式采样。** `qrcode-1`（77 个定位/0 个解码）和 `qrcode-6`（60 个/0 个）是
  更高版本的符号：采样器从三个探测器中心构建一个纯粹的**仿射**网格，该网格漂移
  一个大的或透视扭曲的符号。使用右下角**对齐图案**
  对于四点透视变换（如 ZXing 的 `Detector` 所做的那样）是匹配的 QR 胜利。
- **数据矩阵大小调整 + 极性。** 单个 `inverted` 数据矩阵现在位于极性翻转之后，但
  定位器尺寸错误（10 位数字符号为 22×22，其真实尺寸约为 12–14），因此无法解码；一个
  全帧反极性重试已原型化，但在此步骤中恢复，因为它使语料库扫描时间加倍
  零净语料库获胜（阻碍因素是 DM 大小，而不是极性）。一旦 DM 定位器返回，倒置支撑应返回
  尺寸调整被收紧，范围被限制，因此额外的通道仅在否则会失败的帧上运行。
- **Aztec 采样。** `aztec-1`（68 个定位/0 个解码）：找到了靶心，但轴对齐的网格采样没有找到
  尚未恢复这些捕获。

### 步骤 3 — GS1 DataBar (RSS-14) 编码 + 解码 + 定位器_（RSS-14 完成）_

- **`gs1-databar-common`** — 从 ZXing 的 `RSSUtils` 移植的 ISO/IEC 24724 组合原语：`combins`，

  宽度比方差查找器匹配器。单元测试断言每个 RSS-14 上的值/宽度映射都是自逆的
  子集。
- **`gs1-databar-decode`** — ZXing `RSS14Reader` 的忠实移植：finder 检测、`parseFoundFinderPattern`、

- **`gs1-databar-encode`** — 值→模块位反转。它的物理布局（防护栏、外部/取景器/内部元素

### 第 4 步 — PDF417 编码 + 解码 + 堆叠行定位器_（完成）_

新的 crate trio 镜像了存储库的 `*-common` / `*-encode` / `*-decode` 拆分，移植了 `com.google.zxing.pdf417.*`
（阿帕奇-2.0）：

- **`pdf417-common`** — 双方需要的共享表和数学：符号 ↔ 码字表（2,787 个条目，
  从 ZXing 参考生成）、码字/簇查找（`get_codeword`、`bucket_from_symbol`）、
  模块位计数 → 符号采样器（精确的快速路径加上延迟构建的最接近比率后备），以及 **GF (929)
  Reed–Solomon** 纠错解码器（`ModulusGF` / `ModulusPoly` / 欧几里得算法）。单元测试断言每个
  码字值在三个簇和往返中的每一个中都有一个符号。
- **`pdf417-decode`** — GF (929) EC 校正加上高级位流解析器 (`DecodedBitStreamParser`) 覆盖
  **文本**、**字节**和**数字**
  压实。它使用定位器组装的平面码字数组并返回有效负载。
- **`pdf417-encode`** — 字节压缩编码器（任何字节负载精确往返）、维度大小、
  EC 码字生成器（`EC_COEFFICIENTS` 适用于所有九个 EC 级别，从参考生成）和模块矩阵
  布局（启动/停止防护装置、左/右行指示器）。它公开了码字数组（对于码字级
  往返）和打包模块位图（用于图像路径测试）。

扫描仪获得 `crates/code-scan/src/pdf417.rs`。 PDF417 是_堆叠线性_
符号系统，因此定位器一次扫描一行：在每个图像行上，它找到起始防护，读取 17 模块
代码字（每个条形/空格运行 8 个）直至停止防护，对行中的列/行计数/EC 级元数据进行投票
指示器，将数据码字放入 `rows × cols` 矩阵（跨扫描线的每个单元格的多数投票）
覆盖每个条形码行）并将其交给 RS 检查的解码器。第二遍从右到左读取每一行，因此
180° 旋转的符号仍然可以解码。它作为 `FORMAT_PDF417` 连接到 `scan_and_decode`。

事实证明，两个稳健性细节至关重要：

- **热路径中仅精确采样。** 每次运行采样器仅使用精确匹配
  （`sample_codeword_symbol_exact`）；未完全采样的运行将成为保留列的 `-1` _hole_
  对齐并在投票中被跳过。这使得扫描每张图像的每一行变得便宜——O（表大小）
  否则，最接近比率的后备将主导语料库扫描。
- **防止 RS 过度校正的孔防护装置。** 由于 EC 水平较高，Reed-Solomon 将很乐意制造一个
  来自大部分为空的程序集的_有效但错误_代码字（观察为垃圾 `"AAAA…"` 解码）。因此定位器
  当孔数超过 `num_ec / 2`（RS 校正预算）时拒绝解码，这删除了**每个**
  垃圾解码，同时保留所有正确的 - 并保持负文件夹误报防护干净。

一路上修复了一个错误：位流解析器的默认臂可能会在损坏的流上永远旋转（重新运行文本
压缩它无法消耗的码字）；现在，当它没有取得任何进展时，它就会放弃。

**结果：** `pdf417-1` / `pdf417-2` / `pdf417-3` 从 **0 → 8 / 13 / 8**
在旋转 0 处正确解码，并在 180° 处再次正确解码（**58** 在旋转中正确解码），在任何其他旋转中**无回归**
文件夹和负文件夹仍处于**零**误报。往返行程包括
`pdf417-decode/tests/roundtrip.rs` 和 `code-scan/tests/generated.rs`，以及完整图像路径（编码 → 渲染 →
`scan_and_decode`，包括。 180°）由
`code-scan/tests/pipeline.rs`。

**下一个 PDF417 迭代：** 旋转 **90°/270°** 保持在基线 0 — 四分之一圈符号呈现为垂直条
行扫描定位器不读取。列扫描（转置）通道，或馈送转置帧的线束，是
匹配的后续。更陡的倾斜需要完整的 ZXing 四角 `Detector` 透视模型。

### 第 7 步 — 用于相机 UPC/EAN 照片的 ZXing 式每位数一维行解码器_（完成）_

剩余的主要语料库故障模式是**定位但未解码**一维条形码。原始一维路径
(`barcode.rs` → `barcode-decode`) 通过量化每个候选扫描线将每个候选扫描线采样到模块位的平坦运行中
针对**单个全局模块单元**运行。这在干净的上传上是准确的，但在相机照片上，模块宽度是
整个符号并不恒定——透视、模糊和不均匀的印刷拉伸了它——所以一个全球单位可以围绕多个单位
元素针对错误的网格，并且严格的 EAN/UPC 单元解码器拒绝结果。该符号位于_定位_ (`scan`
返回候选扫描线）但从未_解码_。

该修复是一个新的 `crates/code-scan/src/barcode_row.rs`，它是 ZXing 的 `UPCEANReader` 系列的忠实移植。它从来没有
量化为全局网格：它逐个模式地遍历扫描线，并且对于 **每个数字独立**，进行标准化
在将其与 L/G/R 宽度表进行匹配之前，将该数字的四个运行宽度分配给七个模块单元
（`patternMatchVariance` 与 `MAX_AVG_VARIANCE` /
`MAX_INDIVIDUAL_VARIANCE`）。因为每个数字都带有自己的本地单位，所以符号上的逐渐漂移不再
击败阅读。它涵盖 **EAN-13 / UPC-A**（通过 EAN-13，从六个左半部分恢复前导数字）
奇偶校验位）、**EAN-8** 和 **UPC-E**（之前没有_解码路径 — `barcode-decode` 中不存在该路径）
符号系统列表），重用共享条形码带检测器来选择扫描行。它在 `decode_barcode_frame` 中作为
网格解码器失败后的回退，因此干净的上传可以保持快速路径。

两名警卫将负数文件夹的误报率保持在**零**——读者比网格更宽容
量化器，所以两者都是必不可少的：

- **两侧都有安静区域。** ZXing 要求尾部安静区域至少与端护罩一样宽（镜像
  现有的启动保护安静区）。如果没有它，`1:1:1` 会在不相关的符号内部运行一个虚假的“条形码”
  与巧合的有效校验和相结合，解码了最初 9 + 12 个误报的来源
  `falsepositives*`。
- **短符号的多行共识。** 8 位 EAN-8 / UPC-E 容易出现侥幸校验和有效
  框架混乱，因此仅当 **≥ 2 扫描行** 独立解码相同的值（真正的
  条形码在其条高度的许多行上进行解码；侥幸出现在其中之一）。 13 位 EAN-13 / UPC-A（12 个数据位
  加上奇偶校验得出的前导数字）
  的可能性要小得多，并且可以从单行中接受。每个返回值还由符号的验证
  拥有 mod-10 校验和。

**结果：** 在 UPC/EAN 文件夹中，旋转 0 急剧上升 - 例如
`ean13-3` **3 → 54**，`upca-2` **0 → 31**，`upce-2` **0 → 37**，`upca-5`
**13 → 26**，加上 `ean13-1`、`ean8-1`、`upca-1`、`upce-1/3` 并且，因为回退也运行在
拉直并重试帧，90°/180°/270° 处的增益相当（例如 `upce-2` rot90 **0 → 35**）。 **没有**其他文件夹
回归且负文件夹（`falsepositives`、`falsepositives-2`、`unsupported`）保持 **零** false
积极的一面。两个语料库支持的回归测试
`code-scan/tests/pipeline.rs` 锁定真实的 UPC-E/EAN-13/EAN-8 照片读取和干净的误报防护，以及 JS
Smoke Suite 通过上传和流媒体路径获取 UPC-E + EAN-13 相机照片。

**注意 — `img.png`。** 工作空间根真实世界捕获 (`real_world.rs`) 现在已_定位_干净，但它编码
经典生成器示例 `01234567`
其尾随数字**不是**有效的 mod-10 检查（`0123456` → `01234565`）。符合规范的阅读器 - 这个，以及
ZXing 本身 - 拒绝未通过自身校验和的条形码，因此管道_按照设计_不会返回任何值；那个
测试保留 `#[ignore]` 作为有意拒绝的文档（删除校验和保护来读取它将
