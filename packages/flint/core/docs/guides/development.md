# Develop Flint

This guide is for contributors changing the Flint parser, checked
contracts, or conformance fixtures.

## Install and check the package

From the repository root, install dependencies and run the package checks:

```bash
pnpm install
pnpm --filter @mission-platform/flint build:check
pnpm --filter @mission-platform/flint test
```

Run `pnpm --filter @mission-platform/flint build` before publishing.
The build emits the browser-safe bundle and declaration files under `dist/`.

## Add a language change

Update the grammar and the checked frontend together. Add a focused fixture to
`src/fixtures/` and a regression test for diagnostics or generated behavior.
Keep language version `1.0` and ABI version `1.2` explicit unless the change is
an intentional compatibility revision. ABI changes must update manifests,
loaders, and the compatibility documentation.

The package is browser-safe. Do not add Node-only APIs to the public facade;
Node-specific tooling belongs in `@mission-platform/flint-cli`.

## Generated and source artifacts

The checked-in `.flint` sources under `src/self-hosted/fws/` are source artifacts,
not hand-copied JavaScript. Keep generated output in `dist/` and do not commit
local build output. The package documentation reference is maintained beside
the package and will be regenerated by the documentation extraction workflow.

## Inspecting the two-stage pipeline

The canonical frontend boundary is the deterministic Sea-of-Nodes graph. The
graph is optimized before lowering to Wasm IR, where a second optimizer applies
backend-safe propagation, dead-code removal, address simplification, switch
lowering, and deterministic layout. Keep both stages auditable: optimizer
reports and the selected bounds policy must be retained in compiler artifacts.

Use runtime bounds checks unless a proof-producing rule establishes every
access as safe. `proven-safe` and `excluded-by-profile` are explicit policy
values, not implicit release behavior. A `.sonir.json` cache artifact is
diagnostic data only; readers must validate its schema, hashes, policy, and
limits before displaying it, and must never execute graph contents.

For CLI smoke checks:

```bash
flint check src/example.flint --bounds-checks runtime --optimizer-report --format json
flint inspect-sonir .cache/example.sonir.json --format json
```

When changing analysis, add facts and a stable diagnostic test before changing
an optimization rule. Development analysis should expose unknown ranges,
alias/lifetime states, switch coverage, and pass metadata; strict analysis must
block unsafe bounds-policy requests and region/ownership violations.
