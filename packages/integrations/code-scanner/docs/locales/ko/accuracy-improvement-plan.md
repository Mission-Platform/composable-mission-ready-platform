원래 구현에서는 파이프라인을 분할했습니다.

- **찾기 + 샘플**은 레거시 네이티브/wasm 파이프라인: `binarize` → 기호별 로케이터에서 실행되었습니다. `scan` 진입점
  **태그가 지정된 버퍼** `[format, ...payload]`를 반환했습니다. — 디코딩하지 **않았습니다**.
- **디코드**는 JavaScript로 실행되었으며 별도의 디코더 모듈을 호출했습니다.

1단계에서는 이를 단일 FWS `scan_and_decode` 호출로 대체했습니다(§1 참조). 는
아래의 역사적 동기는 근거로 유지되는 반면, 현재의 출처는
진실은 FWS 그래프와 Vitest 적합성 제품군입니다.

## 1. 핵심 구조적 문제: 파이프라인이 wasm ← JS 경계를 두 번 넘었습니다.

1단계 이전 단일 스캔은 다음과 같습니다.

```
image (JS)
  → wasm code-scan.scan()            [Rust: binarise + locate + sample]
  → tagged module buffer (JS)        [cross back into JS]
  → decodeQr / decodeMatrix / decodeBarcode (JS façades)
  → wasm qr/matrix/barcode-decode    [cross into a *different* wasm module]
  → payload string (JS)
```

찾은 모든 기호는 wasm에서 복사되고 JS에서 모양이 변경된 다음 두 번째 wasm 인스턴스에 복사되어 디코딩됩니다. 이것은
문제가 호출하는 왕복 여행. 성능이 저하되고 이 계획에서 더 중요한 것은 **정확성**이 저하됩니다.
로케이터와 디코더는 협력할 수 없습니다:

- **로케이터에 대한 디코드 피드백이 없습니다.** Rust 로케이터는 _single_에 커밋됩니다.
  이진화, 기호 크기 및 모듈 그리드. JS 디코더에서 샘플링된 그리드가 리드-솔로몬/체크섬에 실패하면
  다른 임계값, ±1 모듈 크기 또는 이동된 원점으로 다시 샘플링하도록 로케이터에 요청할 방법이 없습니다. 다음과 같은 코드
  _위치는 있지만 디코딩할 수 없습니다_(디버그 로깅이 목표로 하는 정확한 경우)
  단순히 손실되었습니다.
- **손실이 있는 핸드오프.** 로케이터는 풍부한 중간 상태(회색 레벨, 후보 검색기 센터, 모듈별)를 평면화합니다.
  디코더가 보기 전에 하드 `0/1` 비트까지 내려갑니다. 그런 다음 디코더는 비트만으로 작동합니다.
- **기호 우선순위는 무뚝뚝한 도구입니다.** 1D 코드의 경우 JS 측은 고정된 순서로 기호를 시도하고
  읽은 첫 번째 항목을 반환합니다. UPC-A는 선행 0이 있는 EAN-13의 모듈 수준 하위 집합이기 때문에 UPC-A 기호는 다음과 같습니다.
  EAN-13으로 보고되었습니다(새 테스트 모음에서 확인됨). Rust에서 디코딩하면 로케이터가 구조적 힌트(요소
  카운트, 가드 패턴)을 사용하여 올바른 기호를 선택하세요.

### 대상 아키텍처 — FWS 호출 1개, 이미지 입력, 페이로드 출력

> **상태: 구현됨.** 스캐너는 `scan_and_decode`을 내보내고
> 디코더 FWS 그래프를 직접 작성하고 JS façade는 해당 단일을 통해 디코딩합니다.
> 전화하세요. 아래 세부정보에는 마이그레이션 근거가 기록되어 있습니다.

```
image (JS)
  → FWS scanner.scan_and_decode()      [binarise + locate + sample + decode]
  → ScanOutcome { format, value } (JS)
```

`scan_and_decode(width, height, luma) -> Option<ScanOutcome>`은 `src/fws/scanner.fws` 내부에서 전체 파이프라인을 실행하고
**디코딩된 페이로드**를 직접 반환합니다(기호가 있지만 디코딩할 수 없는 경우 `value`는 비어 있음). JS 파사드
(`scanner/index.ts`)은 빌드 시 QR, 매트릭스 및 바코드 FWS 소스를 연결하는 얇은 마샬링 레이어입니다.
해당 패키지는 독립적으로 게시 가능한 상태로 유지됩니다.

#### 이것이 지금 다루기 쉬운 이유

디코더 상자에는 이미 일반 Rust 코어와 `crates/code-scan`이 노출되어 있습니다.
**이미 기본 테스트를 위해 링크되어 있습니다**(`tests/pipeline.rs` 호출
`mission_platform_barcode_decode::decode_modules`,
`mission_platform_matrix_code_decode::decode` 등). 그들이 갇혀 있는 유일한 이유는
`[target.'cfg(not(target_arch = "wasm32"))'.dev-dependencies]`는 각 디코더 상자가
`#[wasm_bindgen] pub fn decode`, 그 중 여러 개를 하나의 cdylib로 연결하면 내보낸 `decode`에서 충돌이 발생합니다.
상징.

수정 사항은 소규모의 기계적 리팩터링이었습니다. **이제 네 단계가 모두 완료되었습니다**:

1. **모든 디코더에는 `#[wasm_bindgen]`이 _아님_ 일반 Rust 진입점이 있습니다**
   (`decode_modules`, `decode_matrix`, `decode_qr`) 및 `#[wasm_bindgen]`
   `decode`/`start` 내보내기는 새로운 `wasm-api` 크레이트 기능(기본적으로 켜져 있고 `console`에 의해 암시됨)을 통해 제어됩니다.
2. **`code-scan`는 `default-features = false`이 포함된 디코더 상자에 따라 다릅니다**
   (따라서 `wasm-api`은 꺼짐), 개발 종속성에서 실제 종속성으로 승격되었습니다. wasm-bindgen `decode` 기호가 없습니다.
   스캐너 cdylib로 컴파일되므로 충돌이 없습니다. 스캐너 wasm을 다시 빌드하여 확인합니다.
3. `crates/code-scan/src/lib.rs`의 **`scan_and_decode`**은 처리 중인 디코더의 일반 Rust 코어를 찾아 호출합니다.
   그리고 `ScanOutcome { 형식을 반환합니다.
디코딩할 수 없는 경우 값 }` (a `#[wasm_bindgen]` struct; `value` is `undefine`).
4. **JS 외관이 슬림해졌습니다**: `decodeTagged` 라우팅과 세 가지 디코더 패키지 가져오기가 사라졌습니다.
   단일 `scan_and_decode` 호출로 대체되었습니다.

이제 찾기 및 디코딩이 하나의 주소 공간을 공유하므로 이는 아래의 모든 정확도 향상을 위한 활성화 단계입니다.

## 2. Rust에서 디코딩하면 정확도가 향상됩니다.

대략적으로 예상되는 읽기 속도 영향을 기준으로 정렬되었습니다. **항목 1~~3(2단계) 및 항목 4~~7(3단계)이 완료되었습니다**; 각각은
아래에 주석을 달았습니다.

1. **로케이터 ⇔ 디코더 재시도 루프. _(완료 — 2단계.)_** 첫 번째 디코딩 시도가 실패하면 `scan_and_decode`
   Rust를 떠나지 않고 다시 샘플링합니다. 두 번째(적응형) 이진화, 하위 모듈 원점 이동을 시도합니다.
   (`SAMPLE_OFFSETS`), 삭제 인식 및 블라인드 디코딩 모두, 기호의 통과하는 첫 번째 후보를 수락합니다.
   자체 오류 수정. 이는 _위치는 있지만 디코딩할 수 없는_ 오류를 직접 공격합니다.
2. **로컬/적응형 이진화. _(완료 — 2단계.)_** `image::binarize`(글로벌 **Otsu**)가 빠른 첫 번째로 유지됩니다.
   시도; `image::binarize_adaptive`은 창으로 표시된 **로컬 평균 C** 임계값(적분 이미지를 통해)을 추가하여 눈부심을 유발합니다.
   그라데이션과 고르지 않은 조명은 더 이상 어두운 모듈을 배경에 병합하지 않습니다. 재시도 루프는 두 가지를 모두 시도합니다.
3. **그레이 레벨(하위 픽셀) 모듈 샘플링. _(완료 — 2단계.)_** `qr` 및
   `datamatrix`는 이중선형을 사용하여 _회색_ 이미지에서 모듈 중심을 샘플링하는 `scan_with_confidence`을 얻었습니다.
   보간하고 로컬 임계값 근처의 모듈을 신뢰도가 낮은 것으로 표시합니다. 이는 디코더로 전달됩니다.
   (`decode_qr_with_erasures` / `decode_matrix_with_erasures`) Reed–Solomon **삭제**로서
   오류 및 삭제 교정기(`gf`, `reed_solomon`)
   알 수 없는 오류 발생률이 최대 2배 더 높습니다.
4. **1D 및 데이터 매트릭스에 대한 다중 규모 + 회전 견고성. _(완료 — 3단계.)_** QR 로케이터는 이미
   세 개의 파인더 센터를 통해 회전이 가능합니다. Data Matrix는 이제 **모든** 회전에서 읽습니다. 즉, 코너 기반 아핀입니다.
   로케이터(`scan_oriented_candidates` - 4개의 극단적인 잉크 모서리, solid 모서리에서 감지된 L 모서리,
   평행사변형 규칙에 의해 재구성된 반대편 코너, 타이밍 에지에서 크기 판독, 독립적인 샘플링
   열/행 축이므로 전단도 처리됩니다)
   적당한 각도를 커버하고 직선화 및 재시도 폴백으로 가파른 각도를 복구합니다. `Bitmap::orientation`는
   최소 영역 경계 상자 스윕을 통한 회전(극점 모서리가 퇴화되는 45° 제품군에서 강력함),
   `image::rotate_luma`은 프레임을 직선화하고 튜닝된 직립 파이프라인이 이를 샘플링합니다. 1D 바코드가 처리됩니다.
   같은 방식으로 — 기울기가 복구되고 프레임이 곧게 펴집니다(네 가지 축 정렬 방향이 모두 시도됨).
   수평 주사선이 막대를 교차합니다. 다양한 각도에 걸쳐 회전 캡처 파이프라인 테스트가 적용됩니다(
   45°/90°/180°+) 및 강화된 JS 저하 프로파일.
5. **1D에 대한 기호 명확성. _(완료 — 3단계.)_** UPC-A 대 선행 0-EAN-13 모호성은 다음과 같이 해결됩니다.
   **숫자 체계 숫자**:
   `decode_any_barcode`는 다음을 통해 우승한 기호를 후처리합니다.
   `disambiguate_symbology`는 숫자 체계 숫자가 다음과 같은 EAN-13을 보고합니다.
   `0`은 12자리 UPC-A 형식(앞에 0이 제거됨)이며 정품 EAN-13은 그대로 유지됩니다. _남은 것:_ 운반
   더 풍부한 위치의 구조(가드 바 위치, 요소 수)를 결정에 반영하고 의도한 기호를 노출합니다.
   호출자가 이를 제한할 수 있습니다.
6. **아즈텍 지원. _(완료 — 3단계.)_** `@mission-platform/matrix-code`
   인코더는 이미 Aztec을 생성했지만 스캐너에는 Aztec _locator_가 없습니다. 소형 아즈텍 불스아이 로케이터 추가
   (`crates/code-scan/src/aztec.rs`): 9회 실행된 `1:1:1:1:1:1:1:1:1` 파인더 서명으로 중앙 불스아이를 찾습니다.
   (내부 7개 실행은 신뢰할 수 있고 외부 2개는 모드 링에 닿기 때문에 존재해야 함) 두 축에서 이를 확인합니다.
   모듈 크기를 복구하고, 얼룩이 제거된 사본에서 각각의 그럴듯한 소형 크기(15/19/23/27)를 샘플링하고 각각 라우팅합니다.
   모드 메시지 + Reed–Solomon 검사가 잘못된 크기를 거부하는 기존 Aztec 디코드 경로로 이동합니다. `scan_and_decode`
   `FORMAT_AZTEC`로 보고합니다.
7. **다중 기호 + ROI 스캐닝. _(완료 — 3단계.)_** `scan_and_decode_all`
   모든 고유한 디코딩된 기호(전체 프레임의 대략적인 스윕, 겹치는 절반 및 사분면,
   `(format, value)`에 의해 중복 제거됨)
   `scan_and_decode_roi`는 **이전에 Rust에서** 호출자 제공 영역을 자릅니다.
   이진화하므로 레티클 자르기는 주변의 혼란스러운 요소를 전면에서 거부합니다. 둘 다 JS 외관에 표시됩니다.
   (`scanImageDataAll`, `scanImageData(image, roi)`).

## 3. 검증 전략

작업의 정확성은 눈으로 확인하는 것이 아니라 측정해야 합니다.

- **생성된 이미지 왕복 테스트.**
  `src/scanner/index.spec.ts`은 다양한 인코더 출력을 렌더링합니다(크기/UTF-8 전체에 걸쳐 5개의 QR 페이로드와 4개의 ECC 모두 포함).
  레벨, 4개의 데이터 매트릭스 페이로드, 7개의 1D 기호(`code128`, `code39`, `ean13`, `ean8`, `upca`, `itf`,
  `codabar`) — 그리고 전체 `render → locate → sample → decode` 경로를 확인합니다(현재 단일

1. **단계 0 — 테스트(완료).** 생성된 이미지 모음을 확장했습니다(시드된 측면/회전/기울기/모프/노이즈 포함)
   저하) 따라서 리팩토링 전에 파이프라인에 안전망이 있었습니다.
2. **1단계 — 디코드를 Rust로 통합합니다(완료).** 종속성/기능 리팩터링 + `scan_and_decode` + JS 외관
   슬림다운. 행동 보존; 왕복, 파이프라인 및 새로운 `scan_and_decode` 테스트를 통해 검증되었으며

3. **2단계 — 이진화 + 하위 픽셀 샘플링 + 재시도 루프(완료).** 적응형 로컬 이진화, 회색 이중선형
   Reed-Solomon 삭제로 디코더에 공급되는 모듈별 신뢰도로 샘플링하고 전역 → 적응형 ×
   `scan_and_decode`의 삭제/블라인드 × 원점-오프셋 재시도 루프 — 가장 큰 읽기 속도 승리, 이제 찾기 및
   디코드는 하나의 Rust 호출에 협력합니다.
4. **3단계 — 회전/비뚤어짐, 기호 명확성, 아즈텍, 다중 기호(진행 중).** 1D 기호
   명확성(§2 항목 5)이 시작되었습니다. 남은 금액:
   데이터 매트릭스/1D 회전-스큐 허용오차(항목 4), Aztec 로케이터(항목 6) 및 다중 기호 + ROI 스캐닝(항목 7) - 각각 자체 저하 매트릭스 델타 뒤에 도달했습니다.

### 2단계 — 지원되는 형식의 읽기 속도 높이기 _(진행 중)_

분류(디코딩됨/잘못된 값/위치는 있지만 디코딩되지 않음/로 모든 이미지/회전의 폴더별 분류)

이제 파이프라인은 **거의 모든 것을 찾아내지만** **깨끗한 캡처만 디코딩**합니다. 남은 실패는
압도적으로 _위치는 있지만 디코딩되지 않은_, _위치가 없는_ 것은 아닙니다.

**이 단계에 도달했습니다:**

- **ITF 거짓 긍정 가드.** Interleaved-2-of-5에는 검사 숫자가 없고 사소한 시작/중지가 없으므로 스캔 라인이 교차합니다.
  관련 없는 기호(QR, 기타 막대)는 허위 2자리 또는 4자리 값으로 사소하게 "디코딩"됩니다. 현재 `itf::decode`
  **6자리**보다 짧은 페이로드를 거부하며 ZXing의 `ITFReader::DEFAULT_ALLOWED_LENGTHS`의 하한과 일치합니다.
  (`{6,8,10,12,14}`). 이로 인해 `falsepositives`, `falsepositives-2` 및 `unsupported`의 오탐지가 발생하여
  **제로** 그리고 우선순위 순서를 단락시키는 짧은 읽기를 제거함으로써 몇 가지 긍정적인 결과를 얻었습니다.
  폴더(예: `qrcode-4`, `qrcode-5`). 새로운 회귀 테스트(`barcode-decode`:
  `itf_rejects_runs_shorter_than_six_digits`) 및 기준 업데이트.

**정량화된 다음 기회(찾았으나 아직 해독되지 않음):**

- **자리당 1D 행 디코딩(가장 큰 기회).** UPC/EAN 폴더는 수백 개의 스캔 라인을 찾지만 거의 디코딩됩니다.
  하드 카메라 사진이 없습니다(`upca-2` 206 위치/0 디코딩, `upce-2` 160/0, `ean13-3` 204/6). 근본 원인
  로케이터는 모듈 비트를 모듈에 전달하기 전에 각 스캔 라인을 **단일 전역 모듈 단위**로 양자화한다는 것입니다.
  디코더; 원근 단축법에 따라 실제 모듈 너비는 기호에 따라 달라지므로 전역 그리드가 표류합니다.
  엄격한 EAN/UPC 셀 그리드는 이를 거부합니다. 수정 사항은 각 숫자의 숫자와 일치하는 ZXing 스타일의 **숫자별** 행 디코더입니다.
  전역 양자화 대신 로컬로 실행 길이 비율(패턴 일치 분산)을 적용합니다.
  로케이터-디코더 인터페이스, 다음 2단계 반복으로 추적됩니다.
- **QR 관점/정렬 패턴 샘플링.** `qrcode-1`(77 위치/0 디코딩) 및 `qrcode-6`(60/0)는
  상위 버전 기호: 샘플러는 세 개의 파인더 센터에서 순전히 **아핀** 그리드를 구축합니다.
  크거나 원근감이 왜곡된 기호. 오른쪽 하단 **정렬 패턴** 사용
  4점 원근 변환(ZXing의 `Detector`와 마찬가지로)의 경우 QR 일치가 승리합니다.
- **데이터 매트릭스 크기 조정 + 극성.** 단일 `inverted` 데이터 매트릭스는 이제 극성 반전 후에 위치하지만
  로케이터에 의해 크기가 잘못되어(실제 크기가 ~12-14인 10자리 숫자 기호의 경우 22×22) 디코딩되지 않습니다. 에
  풀프레임 역극성 재시도가 프로토타입화되었지만 코퍼스 스윕 시간이 두 배로 늘어났기 때문에 이 단계에서 되돌렸습니다.
