# שיטות עבודה מומלצות לפלטפורמת המשימה

תרגום בסיוע מכונה מהמקור האנגלי הקנוני. יש לבדוק ידנית בעת הצורך. שמות חבילות, פקודות, נתיבים ומזהים טכניים נשארים ללא שינוי.

> docs/best-practices.md: [docs/best-practices.md](../../best-practices.md)
> שפה: עברית (he)

מסמך זה מתאר את עקרונות הליבה, הארכיטקטורה ותקני הקידוד עבור פלטפורמת המשימה monorepo. זה
משמש כ**הסבר** מדוע אנו עוקבים אחר דפוסים מסוימים ו**קו מנחה** לפיתוח יומיומי.

## עקרונות ליבה

### אדריכלות מתאימה

Mission Platform עוקבת אחר ארכיטקטורה מונעת חבילה וניתנת להרכבה. אבני בניין לשימוש חוזר (רכיבי ממשק משתמש,
חומרים מורכבים, כלי עזר) חיים ב-`packages/`, בעוד שיישומים הניתנים לפריסה מורכבים מהבלוקים האלה ב-`apps/`.

### משמעת תלות

כדי לשמור על monorepo בר תחזוקה, אנו אוכפים זרימת תלות חד כיוונית קפדנית:

- **`apps`** → **`packages`**
- **`packages`** → חבילות דומיין ברמה נמוכה יותר כגון **`core`**, **`tooling`** ו-**`compiler`**

**כלל:** קוד ב-`packages/` חייב **לעולם לא** לייבא מ-`apps/`. זה מונע תלות מעגלית ומבטיח
החבילות נשארות ניתנות לשימוש חוזר באמת.

### ספר סיפורים כשולחן עבודה

בעת הוספה או שינוי של רכיבים ב-`packages/`, השתמש באפליקציית Storybook (`apps/storybook`) בתור הפיתוח העיקרי שלך
סביבה. אפליקציית `apps/storybook` אינה מכילה את הסיפורים עצמם - זה שולחן העבודה המצטבר
מגלה ומציג את הסיפורים שחיים לצד מרכיביהם.

- אתר יחד כל קובץ `.stories.tsx` עם הרכיב שלו בתוך ספריית החבילות של אותו רכיב (למשל.
  `packages/ui/components/src/components/**/<component>/<component>.stories.tsx`), לא תחת `apps/storybook`. זה תואם
  האמנה ב-[עיצוב רכיבים אטומיים](atomic-component-design.md).
- אמת את התנהגות הרכיבים על פני Vue, React, Svelte, Solid ורכיבי אינטרנט על ידי החלפת
  משתנה סביבה `STORYBOOK_FRAMEWORK`. כל מצב חייב לצרוך את אותו מלאי סיפור ניטרלי; חסר
  חפץ מסגרת הוא כשל בחבילה/ייצוא, לא סיבה לסנן את הסיפור הזה החוצה.

לולאת האימות הסטטית המלאה היא:

```bash
for framework in vue react svelte solid web-component; do
  STORYBOOK_FRAMEWORK="$framework" pnpm --filter @mission-platform/storybook run build-storybook
done
```

## תקני פיתוח

### TypeScript בכל מקום

כל קוד המקור החדש חייב להיכתב ב-TypeScript (`.ts`) או Vue SFCs עם `<script setup lang="ts">`.

- **מצב קפדני**: `strict: true` נאכף בכל קבצי `tsconfig.json`.
- **סוגים מפורשים**: ספק סוגים מפורשים עבור כל ממשקי ה-API הציבוריים, הפונקציות המיוצאות ורכיבי החיבור.
- **הימנע מ-`any`**: השתמש בסוגים מדויקים או כלליים. אם סוג אינו ידוע באמת, השתמש ב-`unknown` ובצע צמצום סוג.

### רכיבים ניטרליים במסגרת

במידת האפשר, מחבר רכיבי ממשק משתמש באמצעות הניב `@mission-platform/forge-jsx`. זה מאפשר לרכיבים להיות
הידור והשימוש ב-Vue, React, Svelte, Solid ו-Web Components מבלי לשכתב את לוגיקה הליבה. הגדר את
הפותר של הצרכן עם המצב התואם `mp:vue`, `mp:react`, `mp:svelte`, `mp:solid` או `mp:web-component`.

### דפוסי תגובתיות (Vue 3)

- השתמש ב-**Composition API** באופן בלעדי.
- העדיפו `ref()` עבור רוב המדינה כדי לשמור על עקביות.
- חלץ היגיון מצבי מורכב לתוך **Composables** (`useXxx`).
- ודא שכל תופעות הלוואי (צופים, מרווחים, מאזיני אירועים) מנוקים כראוי ב-`onUnmounted`.

## זרימת עבודה של Monorepo

### בידוד של דאגות

- **רכיבי ממשק משתמש חדשים**: שייכים ל-`packages/`.
- **כלי שירות משותפים**: שייכים ל-`packages/`.
- **כלי מוך/פורמט/בנייה**: תצורות משותפות שייכות ל-`packages/tooling/configs/`.

### מוך ועיצוב

סגנון קוד עקבי נאכף באמצעות ESLint ו-Prettier.

- הפעל את `pnpm lint` כדי לבדוק אם יש הפרות.
- הפעל את `pnpm format:write` כדי לתקן אוטומטית בעיות עיצוב.
- הודעות Commit חייבות לעמוד במפרט **Conventional Commits**.

### תחול תלות במעלה הזרם ובדיקות חבילות

ב-monorepo מודולרי, חבילות במורד הזרם מייבאות לעתים קרובות פלטי build (`dist/`) מחבילות במעלה הזרם. כדי למנוע כשלים בבדיקת מצב נקי ולהימנע ממעקב ידני אחר סדר בנייה של ריבוי חבילות:

1. ** תחול בנייה אוטומטי במעלה הזרם (`^build`)**:
   גרפי משימות `turbo.json` מגדירים את `test`, `build:check` ומשימות אימות עם `"dependsOn": ["^build"]`. הפעלת כל משימת בדיקה או בדיקת סוג דרך Turborepo בונה אוטומטית את כל התלות בסביבת העבודה במעלה הזרם תחילה.

2. **ביצוע בהיקף חבילה**:
   כדי לבדוק או לבנות חבילה בודדת ללא קומפילציה ידנית של דרישות קדם:
   - הפעל בדיקות עם תחול:
     ```bash
     pnpm test:package <package-name>
     ```
     או ישירות דרך Turborepo:
     ```bash
     pnpm exec turbo run test --filter <package-name>
     ```
   - בנה חבילה עם התלות שלה:
     ```bash
     pnpm build:package <package-name>
     ```
     או ישירות דרך Turborepo:
     ```bash
     pnpm exec turbo run build --filter <package-name>
     ```

   במסנני Turbo, `<package-name>...` בוחר את החבילה ואת הזרימה שלה
   תלות, `...<package-name>` בוחר את החבילה ואת שלה במורד הזרם
   תלויים, ו-`<package-name>^...` בוחר רק את החבילה במעלה הזרם
   תלות (למעט החבילה עצמה). עוזרי החבילה פועלים במפורש
   הטופס במעלה הזרם (`<package-name>^...`) קודם כל כך ישיר את זרימות העבודה של החבילה
   יש חימום צפוי שניתן לאחסון במטמון; התלות `^build` של גרף המשימות
   נותרה רשת הביטחון לקריאת טורבורפו ישירות.

3. **הקצאת Worktree**:
   כאשר עצי עבודה חדשים של Git מסופקים באמצעות `pnpm worktree:create` או מאתחלים באמצעות `pnpm worktree:setup`, התלות במעלה הזרם עוברת הכנה אוטומטית לפני הפעלת בדיקות אימות, מה שמבטיח שעצי עבודה חדשים שנוצרו פועלים באופן מיידי.

## מיטוב ביצועים

- **פיצול קוד**: השתמש ב-`import()` דינמי עבור תכונות לא קריטיות וספריות גדולות.
- **אופטימיזציה של נכסים**: העדיפו פורמטים מודרניים של תמונה (WebP/AVIF) והבטיחו שכל הנכסים הסטטיים דחוסים.
- **תקורה של תגובתיות**: השתמש ב-`shallowRef` עבור עצמים גדולים שאינם דורשים תגובתיות עמוקה.

## בדיקות ותיעוד

- **פיתוח מונחה מבחן**: כל תכונה חדשה או תיקון באגים צריכים להיות מלווה בבדיקות יחידה (`.spec.ts`).
- **תיעוד Diátaxis**: תיעוד מחבר בהתאם למסגרת Diátaxis (הדרכות, מדריך, הפניה,
  הסבר).
- **TSDoc**: השתמש ב-TSDoc/JSDoc עבור כל השיטות והמאפיינים הפונות לציבור כדי להפעיל אינטליגנציה של IDE.
