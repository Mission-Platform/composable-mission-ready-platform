# בניית מערכת

תרגום בסיוע מכונה מהמקור האנגלי הקנוני. יש לבדוק ידנית בעת הצורך. שמות חבילות, פקודות, נתיבים ומזהים טכניים נשארים ללא שינוי.

> docs/build-system.md: [docs/build-system.md](../../build-system.md)
> שפה: עברית (he)

מסמך זה מסביר את הארכיטקטורה והמכניקה של מערכת הבנייה של פלטפורמת המשימה. זה נועד עבור גבוה
ביצועים, בנייה מצטברת והפצת חבילות מרובות מסגרות.

## ארכיטקטורת ליבה

פלטפורמת המשימה משתמשת במערכת בנייה מדורגת המפרידה בין תזמור משימות לבין קומפילציה של סביבת עבודה בודדת.

### 1. תזמורת משימות (Turborepo)

**Turborepo** הוא המתזמר ברמה העליונה. הוא מנהל את גרף התלות בין סביבות העבודה ומספק מטמון עבור
כל המשימות.

- **צינור המוגדר ב-`turbo.json`**: משימות כמו `build`, `test` ו-`lint` מוגדרות עם התלות שלהן
  (לדוגמה, `build` תלוי ב-`^build`, כלומר יש לבנות תחילה את כל התלות).
- **Hashing**: Turborepo גיבוב קבצי מקור, משתני סביבה ותלות גלובלית כדי לקבוע אם משימה
  ניתן לעשות שימוש חוזר בפלט מהמטמון.
- **מקבילות**: משימות עצמאיות מבוצעות במקביל כדי למקסם את ניצול ה-CPU.

### 2. הידור חבילות (tsdown)

רוב חבילות הספרייה ב-`packages/` משתמשות ב-**tsdown** להידור.

- **מהירות**: נבנה על גבי **Rolldown** (היורש של Rollup מבוסס Rust), ומספק בנייה כמעט מיידית.
- **פירוק**: החבילות נבנות עם `unbundle: true`, תוך שמירה על מבנה המודול המקורי ב-`dist/`. זה
  מבטיח ניעור עצים אופטימלי וניפוי באגים טוב יותר ביישומי צרכנים.
- **שרשור CSS**: תוסף מותאם אישית מקשר מחדש את גיליונות הסגנונות שחולצו אל מודולי ה-JS שבבעלותם, ומבטיח כי
  ייבוא רכיב מושך אוטומטית את הסגנונות שלו.

### 3. חבילת יישומים (Vite)

יישומים הניתנים לפריסה ב-`apps/` משתמשים ב-**Vite** לפיתוח והפקה.

- **הגדרות משותפות**: אפליקציות מרחיבות את `@mission-platform/vite-config` כדי להבטיח צינורות PostCSS עקביים
  החלטה אגנוסטית של מסגרת.
- **תמיכה ב-SSR/SSG**: יישומים כמו `my-care-notes` משתמשים ב-`vite-ssg` ליצירת אתרים סטטיים.

### Forge בניית חבילות

בניית חבילות Forge מוסיפה חזית מהדר ניטראלית לזרימה הרגילה של `tsdown` או Vite. חבילה צורכת מייבאת
תוספי המסגרת שהוא רוצה ומעבירים מופעים מפורשים ל-`tsdownForgeComponentPlugins` או
`tsdownForgeHookPlugins` בתוך שיחת `defineTsdownLibrary` אחת. הדרייבר הנייטרלי יוצר IR סמנטי פעם אחת, ואז התוסף שנבחר הוא הבעלים של הורדת יעד,
יצירת מקור, הצהרות, רכיבי זמן ריצה חיצוניים ומתאם Vite/tsdown המקורי שלו.

פלט פלטפורמת תוכן הוא ציר שני, אורתוגונלי המוגדר באמצעות `@mission-platform/forge-cms-plugin-api`. א
הצרכן מעביר ל-`tsdownForgeCmsPlugins` רשימה של מופעי `CmsOutputPlugin`, כל אחד
אשר _מרכיב_ תוסף מסגרת - `forgeStoryblokCms({ packageName, plugin, storyblokRuntime })`,
`forgeAstroCms({ packageName, plugin })`, וכן הלאה עבור Ghost, Jekyll ו-Webflow. כי הפלטפורמה וה
המסגרת נבחרות באופן עצמאי, `storyblok × vue` ו-`astro × solid` הם תצורה ולא קוד חדש.

CMS בונה פליטה ל-`dist/cms/<cms>/<framework>/**`, עם מניפסטים ורכבי צד אחרים של פלטפורמה שיקוף לתוך
`dist/cms/<cms>/`. יעדים שזקוקים לזמן ריצה מרופד (Astro, Webflow) יוצרים יחד עץ אי מהתחום
תוסף מסגרת לאותו build. פיצול האחריות המלא וגבולות השלבים מתוארים ב
[Forge Compiler Pipeline](../../../packages/tooling/vite/forge/docs/locales/he/reference/compiler.md).

## בניית חוזה

`pnpm build` הוא המבנה המצטבר הקנוני. הוא מאציל למשימה `build` ברמת החבילה של Turbo מבלי להגדיר
בורר מסגרת, כך שכל חבילת Forge פולטת את הפלט הנייטרלי שלה וכל יעד מסגרת שהוגדר על ידי זה
חבילה. חבילות עם תחזיות CMS פולטות את ההקרנות הללו ואת גלגלי הצד המשותפים שלהן באותו מבנה מדורג.

```bash
pnpm build
pnpm build:force                 # the same aggregate build, ignoring Turbo's cache
pnpm exec turbo run build --filter @mission-platform/components
```

חבילות Forge שומרות גם על כינויי תאימות דקים לבנייה מחדש של יעד אחד:

```bash
pnpm --filter @mission-platform/components run build:forge
pnpm --filter @mission-platform/components run build:vue
pnpm --filter @mission-platform/components run build:react
pnpm --filter @mission-platform/components run build:svelte
pnpm --filter @mission-platform/components run build:solid
pnpm --filter @mission-platform/components run build:web-components
```

הכינויים משתמשים באותו רץ מוקלד כמו `build`; הם אינם מכילים יישומי `tsdown` עצמאיים. `build:forge`
בוחר את היעד הנייטרלי, בעוד שכינויי המסגרת בוחרים את ספריית המסגרת המתאימה. ספציפי לחבילה
פקודות מצב artifact CMS נשארות זמינות היכן שהן נחשפות, כולל פקודת Storyblok assets המשותפת והפקודה
פקודות גלישת Storyblok לכל מסגרת.

### בימוי וקידום

כל קריאת Forge כותבת לשלב מקומי-חבילה ייחודי תחת `node_modules/.cache/forge-build/`. הבמה היא
מתעלמים מהקלט של Turbo ולעולם לא מתפרסם. בנייה מוצלחת נבדקת עבור פלט לפני הקידום:

- **מצב מצטבר** מחליף מבחינה אטומית את העץ השלם `dist` בבעלות Forge. קבצי ניטרליים, מסגרת ו-CMS מיושנים
  לכן מוסרים במקום לספק יצוא בטעות.
- **מצב ממוקד** מחליף מבחינה אטומית רק את תת-עץ המסגרת שנבחר (ותת-העץ התואם שלו ל-CMS העטיפה),
  שימור פלט ניטרלי, מסגרת, דואר אלקטרוני ו-CMS לא קשור כבר ב-`dist`. הרץ חוקר את בורר ה-CMS
  (למשל `FORGE_CMS_STORYBLOK_TARGET`) למסגרת המבוקשת לצד `FORGE_FRAMEWORK_TARGET`, כך ש-CMS של חבילה
  חיווט (`forgeStoryblokCmsTargets` וכו') למעשה בונה מחדש את העטיפה התואמת באותו שלב במקום שהיא תהיה
  ירד בשקט מקידום. קידום מנקה רק תת-עץ של עטיפת CMS שהשלב יצר מחדש; זה אף פעם
  מוחק מעטפת CMS של אח שה-build הנוכחי לא נבנה מחדש.
- לנכסי CMS משותפים כגון סכימות Storyblok ו-`components.json` יש יעד משותף ואינם נמחקים על ידי
  קידום מסגרת מאוחר יותר.
- כשל מהדר, שלב ריק או כשל בקידום מותיר את העץ הקודם שפורסם ללא נגיעה ומסיר את
  מדריך שלב וקידום זמני.

הפלט שפורסם נשאר תחת חוזה `dist` הקיים: מודולים והצהרות ניטרליים, ספריות מסגרת
(`vue`, `react`, `svelte`, `solid`, `web-components`), והקרנות CMS תחת `cms/<cms>/<framework>`. ייצוא חבילה
מפות, כולל תנאי `mp:*` ותת-נתיבי CMS, ממשיכות לפתור נגד נתיבים מקודמים אלה.

### משימות חבילה

| משימה | תיאור |
| :----------------------------------------- | :----------------------------------------------------------------------------------------------------------- |
| `build` | צבר פלט ניטרלי, מסגרת, הצהרה, דואר אלקטרוני ופלט CMS מוגדר דרך ה-Forge runner המשותף. |
| `build:forge` | כינוי תאימות פלט Forge ממוקד ממוקד.                                                           |
| `build:react`, `build:vue`, `build:svelte` | כינויים ממוקדים של תאימות מסגרת.                                                                    |
| `build:solid`, `build:web-components` | כינויים ממוקדים של תאימות מסגרת.                                                                    |
| `build:check` | מאמת סוגים עבור סביבת עבודה מבלי לפרסם פלט.                                                   |
| `build:watch` | מתחיל בנייה מצטברת במצב שעון עבור סביבת עבודה.                                                   |

Turbo מאחז את בוררי היעד (`FORGE_BUILD_TARGET` ובוררי Forge/CMS מדור קודם) יחד עם הבוררים המשותפים
מקורות רץ ובימוי. כתוצאה מכך, בנייה מצטברת וממוקדת לא יכולה לעשות שימוש חוזר זה בתוצאה המאוחסנת של זה במטמון. גמר
פלט `dist/**` שמור במטמון; ספריות בימוי וקידום זמניות אינן נכללות במפורש.

### שלבי בניית אפליקציה

יישומים שיש להם שלבי בנייה משמעותיים באופן עצמאי חושפים את אותם שלבים כמשימות Turbo במקום שרשור
אותם בתוך `build`:

- `@mission-platform/docs` מריץ את `build:check`, `build:bundle`, `build:prerender` ו-`build:verify` לפי הסדר.
- `@mission-platform/figma-forge-plugin` מריץ את `build:check`, `build:ui` ו-`build:main` באמצעות משימת `build` המצטברת שלה.
- `@mission-platform/icons` מריץ את `build:check`, `build:generate` ו-`build:sprite` באמצעות משימת `build` המצטברת שלה.

הסקריפטים המצטברים מאמתים רק שהפלט שבבעלות המשימה קיים; Turbo הוא הבעלים של תזמון, הזמנת תלות ו
שחזור מטמון. זה שומר על השלבים הבודדים ניתנים לצפייה ונמנע קריאות מקוננות של Turbo או בנייה ברמת מעטפת
תזמור.

### אסטרטגיית מטמון

Turborepo מאחסן את החפצים הבאים:

- `dist/**`: חפצי JS/CSS בנויים.
- `.vite/**`: המטמון הפנימי של Vite.
- `coverage/**`: דוחות כיסוי מבחן.

כדי לעקוף את המטמון ולאלץ בנייה חדשה, השתמש בדגל `--force`:

```bash
pnpm build:force
```

ניתן גם לשמור משימות הכרזה בלבד: `build:types` מתעד `dist/**/*.d.ts` ומפות הצהרות כפלטים, כך
בניית סוגים ממוקדים משחזרים את הקבצים הנדרשים על ידי חבילות במורד הזרם.

כינויי התאימות ומשימות מצב artifact CMS הן משימות חבילה, כך ש-Turbo עדיין מיישם את גרף התלות שלהם
כניסות מטמון ספציפיות ליעד. שלבים זמניים אינם פלטי מטמון; רק העץ המקודם `dist` מתפרסם או
שוחזר מהמטמון.

## תצורות משותפות

תצורות Build מרוכזות בספריית `packages/tooling/configs/` כדי לשמור על עקביות ברחבי המונורפו.

| חבילה | מטרה |
| :------------------------------------ | :----------------------------------------------------------- |
| `@mission-platform/vite-config` | לוגיקה Vite משותפת עבור אפליקציות ובניית Vue ספציפיים.          |
| `@mission-platform/tsdown-config` | לוגיקה משותפת של tsdown עבור חבילות ספרייה.                    |
| `@mission-platform/typescript-config` | בסיס `tsconfig.json` מוגדר מראש עבור אפליקציות, ספריות ובדיקות. |
| `@mission-platform/postcss-config` | עיבוד CSS סטנדרטי (Autoprefixer וכו').            |

## שרשרת כלים TypeScript 7

קטלוג סביבת העבודה מצמיד את המהדר ל-TypeScript `7.0.2` יציב. בדיקות סביבת עבודה ובניית הצהרות משתמשים ב-
קובץ הפעלה `tsc` מקורי, בעוד ששילובי עורך משתמשים בשרת שפת האם של TypeScript:

```bash
pnpm exec tsc --version
pnpm exec tsc --lsp --stdio
```

הגדרות קבועות מראש משותפות ב-`@mission-platform/typescript-config` נשארות מקור האמת לרזולוציית יעד, מודול,
סוגי סביבה, הקפדה, הפניות לפרויקט ופלט הצהרות. הכלי Forge ו-CMS אינו משתמש במכשיר שהוסר
TypeScript ממשק API; היא צורכת במקום זאת את חוזי מנתח נייטרלי/OXC שבבעלות המאגר. גם הגבול הזה מסמיך
סורק תיעוד החבילה ושומר על פלט Forge שנוצר ללא תלות ברכיבי ה-API הפנימיים של מהדר.

קובצי JavaScript וקובצי הצהרת הידור נפלטים רק לספריית `dist` של החבילה שבבעלותה. פורג' נוצר
עץ המקור של המסגרת הוא קלט בנייה זמני ומוסר לאחר השלמת החבילה; אסור לו לעזוב את `*.js` או
קבצי `*.d.ts` תחת `src` או ספריות מטמון ברמת החבילה.

הצהרות החבילות של Vue מסונתזות על ידי תוסף הצהרת Forge `tsdown`. נתיב זה פולט חבילה
הצהרות מבלי להפעיל את `vue-tsc`; הוא אינו מספק בדיקת סוגים עבור תבניות SFC של יישומים שרירותיים.
בדיקות SFC של יישומים נשארות שער קבלה מפורש וכרגע דורשות TypeScript 7 תואם במעלה הזרם
שחרור `vue-tsc`. `vue-tsc@3.3.11` הזמין נכשל מול TypeScript `7.0.2` עם
`ERR_PACKAGE_PATH_NOT_EXPORTED` עבור `typescript/lib/tsc`, בעוד `tsc` מקורי אינו בודק בכוונה את `.vue`
קבצים. אל תוסיף כינוי תאימות TypeScript 6 כדי לעקוף את הגבול הזה.

תצורת ESLint המשותפת משתמשת ב-`@babel/eslint-parser` עבור TypeScript, TSX ו-Vue תחביר קטן
תוסף תאימות בבעלות מאגר עבור `@typescript-eslint/no-explicit-any` השמור ו
מזהי כלל `@typescript-eslint/consistent-type-imports`. זה בכוונה תחביר בלבד: הזרם
מהדורת `typescript-eslint` דוחה את TypeScript 7, כך שכללי מוך מודעים לסוג מוחלפים ב-TypeScript המשותף
`noUnusedLocals` ו-`noUnusedParameters` בודקים עד שתהיה מהדורה תואמת במעלה הזרם.

## פיתוח מקומי מול ייצור

### פיתוח (משימה `dev`)

שרת הפיתוח של Vite מספק החלפת מודול חם (HMR). כאשר משימת `dev` של אפליקציה מתחילה, גם Turborepo פועל
משימת `build:watch` של ספריית הרכיבים לצדה (באמצעות מפתח `with` של המשימה), אז עריכה ל
`@mission-platform/components` נערכים מחדש באופן אוטומטי ונאספים על ידי האפליקציה הפועלת ללא בנייה מחדש ידנית.

### הפקה (משימה `build`)

Turborepo מבצע בנייה בסדר טופולוגי. חבילה נבנית רק לאחר שיש לכל התלות הפנימית שלה
נבנה בהצלחה. הפלט ב-`dist/` הוא מה שבסופו של דבר מתפרסם או נפרס.

## מתקדם: שילוב WASM

חבילות מסוימות (למשל, `@mission-platform/hunspell`, סורקי ברקוד) כוללות קוד חלודה שנערך ל-WebAssembly. אלה
בנייה מתוזמרת באמצעות משימות מיוחדות המשתמשות ב-`wasm-pack` כדי להבטיח עקביות סביבתית ואופטימלית
ביצועים.
