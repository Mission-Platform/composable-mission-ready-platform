このドキュメントでは、Mission Platform モノリポジトリの中心となる原則、アーキテクチャ、およびコーディング標準の概要を説明します。それ
これは、特定のパターンに従う理由の**説明**、および日々の開発の**ガイドライン**として機能します。

## 基本原則

### コンポーザブルアーキテクチャ

Mission Platform は、パッケージ駆動型の構成可能なアーキテクチャに従っています。再利用可能なビルディング ブロック (UI コンポーネント、
コンポーザブル、ユーティリティ) は `packages/` に存在し、デプロイ可能なアプリケーションは `apps/` のこれらのブロックから組み立てられます。

### 依存関係の規律

保守可能なモノリポジトリを維持するために、厳密な一方向の依存関係フローを強制します。

- **`apps`** → **`packages`**
- **`packages`** → **`core`**、**`tooling`**、**`compiler`** などの下位ドメイン パッケージ

**ルール:** `packages/` のコードは `apps/` から**決して**インポートしてはなりません。これにより、循環依存関係が防止され、
パッケージは引き続き真に再利用可能です。

### ワークベンチとしてのストーリーブック

`packages/` でコンポーネントを追加または変更する場合は、Storybook アプリ (`apps/storybook`) を主な開発として使用してください。
環境。 `apps/storybook` アプリにはストーリー自体は含まれていません。これは、集約ワークベンチです。
コンポーネントとともに存在するストーリーを発見してレンダリングします。

- 各 `.stories.tsx` ファイルを、そのコンポーネントのパッケージ ディレクトリ内でそのコンポーネントと同じ場所に配置します (例:
  `packages/ui/components/src/components/**/<component>/<component>.stories.tsx`)、`apps/storybook` の下ではありません。これは一致します
  [Atomic Component Design](atomic-component-design.md) の規則。
- Vue、React、Svelte、Solid、および Web コンポーネントにわたるコンポーネントの動作を、
  `STORYBOOK_FRAMEWORK` 環境変数。各モードは同じニュートラル ストーリー インベントリを消費する必要があります。行方不明の
  フレームワークのアーティファクトはパッケージ/エクスポートの失敗であり、その話を除外する理由ではありません。

完全な静的検証ループは次のとおりです。

```bash
for framework in vue react svelte solid web-component; do
  STORYBOOK_FRAMEWORK="$framework" pnpm --filter @mission-platform/storybook run build-storybook
done
```

## 開発基準

### TypeScript どこでも

すべての新しいソース コードは、`<script setup lang="ts">` を持つ TypeScript (`.ts`) または Vue SFC に記述する必要があります。

- **厳密モード**: `strict: true` はすべての `tsconfig.json` ファイルにわたって適用されます。
- **明示的なタイプ**: すべてのパブリック API、エクスポートされた関数、およびコンポーザブルに明示的なタイプを提供します。
- **`any` を回避します**: 正確な型またはジェネリックを使用します。型が本当に不明な場合は、`unknown` を使用して型の絞り込みを実行します。

### フレームワークに依存しないコンポーネント

可能な限り、`@mission-platform/forge-jsx` 方言を使用して UI コンポーネントを作成します。これにより、コンポーネントを
コア ロジックを書き換えることなく、Vue、React、Svelte、Solid、および Web コンポーネントでコンパイルおよび使用されます。を設定します。
`mp:vue`、`mp:react`、`mp:svelte`、`mp:solid`、または `mp:web-component` 条件が一致するコンシューマのリゾルバ。

### 反応性パターン (Vue 3)

- **Composition API** のみを使用してください。
- 一貫性を維持するために、ほとんどの状態では `ref()` を優先します。
- 複雑なステートフル ロジックを **コンポーザブル** に抽出します (`useXxx`)。
- すべての副作用 (ウォッチャー、インターバル、イベント リスナー) が `onUnmounted` で適切にクリーンアップされていることを確認します。

## モノリポジトリのワークフロー

### 懸念事項の分離

- **新しい UI コンポーネント**: `packages/` に属します。
- **共有ユーティリティ**: `packages/` に属します。
- **Lint/フォーマット/ビルド ツール**: 共有構成は `packages/tooling/configs/` に属します。

### リンティングとフォーマット

一貫したコード スタイルは、ESLint および Prettier によって強制されます。

- `pnpm lint` を実行して違反を確認します。
- `pnpm format:write` を実行して、フォーマットの問題を自動的に修正します。
- コミット メッセージは **従来のコミット** 仕様に従う必要があります。

### 上流の依存関係のプライミングとパッケージのテスト

モジュール式モノリポジトリでは、ダウンストリーム パッケージがアップストリーム パッケージからビルド出力 (`dist/`) を頻繁にインポートします。クリーン状態のテストの失敗を排除し、複数パッケージのビルド順序を手動で追跡しないようにするには、次の手順を実行します。

1. **自動アップストリーム ビルド プライミング (`^build`)**:
   `turbo.json` タスク グラフは、`test`、`build:check`、および `"dependsOn": ["^build"]` による検証タスクを定義します。 Turborepo 経由でテストまたはタイプチェック タスクを実行すると、最初に上流のワークスペースの依存関係がすべて自動的に構築されます。

2. **パッケージスコープの実行**:
   前提条件を手動でコンパイルせずに個々のパッケージをテストまたはビルドするには:
   - プライミングを使用してテストを実行します。
     ```bash
     pnpm test:package <package-name>
     ```
     または Turborepo 経由で直接:
     ```bash
     pnpm exec turbo run test --filter <package-name>
     ```
   - 依存関係を含むパッケージをビルドします。
     ```bash
     pnpm build:package <package-name>
     ```
     または Turborepo 経由で直接:
     ```bash
     pnpm exec turbo run build --filter <package-name>
     ```

   Turbo フィルターでは、`<package-name>...` はパッケージとそのアップストリームを選択します
   依存関係の場合、`...<package-name>` はパッケージとそのダウンストリームを選択します
   `<package-name>^...` はパッケージの上流のみを選択します
   依存関係 (パッケージ自体を除く)。パッケージヘルパーは明示的に実行されます
   アップストリーム フォーム (`<package-name>^...`) が最初なので、パッケージ ワークフローを直接指定します
   予測可能でキャッシュ可能なウォームアップを実現します。タスク グラフの `^build` 依存関係
   Turborepo を直接呼び出すためのセーフティ ネットとして残ります。

3. **ワークツリーのプロビジョニング**:
   新しい Git ワークツリーが `pnpm worktree:create` 経由でプロビジョニングされるか、`pnpm worktree:setup` 経由で初期化されると、検証チェックを実行する前に上流の依存関係が自動的に準備され、新しく作成されたワークツリーがすぐに動作できるようになります。

## パフォーマンスの最適化

- **コード分割**: 重要ではない機能や大規模なライブラリには動的 `import()` を使用します。
- **アセットの最適化**: 最新の画像形式 (WebP/AVIF) を優先し、すべての静的アセットが圧縮されていることを確認します。
- **反応性オーバーヘッド**: 深い反応性を必要としない大きなオブジェクトには `shallowRef` を使用します。

## テストと文書化

- **テスト駆動開発**: すべての新機能またはバグ修正には単体テスト (`.spec.ts`) が伴う必要があります。
- **Diátaxis ドキュメント**: Diátaxis フレームワークに従ってドキュメントを作成します (チュートリアル、ハウツー、リファレンス、
  説明）。
- **TSDoc**: IDE インテリジェンスを強化するために、すべての公開メソッドとプロパティに TSDoc/JSDoc を使用します。
