# リポジトリの安全性と検証

正規の英語ソースからの機械支援翻訳です。必要に応じて人手で確認してください。パッケージ名、コマンド、パス、技術識別子は変更しません。

> docs/agent-guidance/repository-safety-and-validation.md: [docs/agent-guidance/repository-safety-and-validation.md](../../../agent-guidance/repository-safety-and-validation.md)
> 言語: 日本語 (ja)

このトピックは、実装、リファクタリング、テスト、生成、リポジトリ検査、ワークツリー、LSP、セキュリティ、およびファイル管理タスクに必須です。ルート `AGENTS.md` に要約された詳細な操作上の制約が保存されます。

## 依存関係の方向と資産の検出

- `packages/` のコードを `apps/` からインポートしてはなりません。アプリケーションは再利用可能なパッケージ メンバーを消費します。ドメイン パッケージは、アプリケーションをインポートせずに、下位レベルの `core`、`tooling`、およびコンパイラ コントラクトに依存する場合があります。
- コードを記述する前に、リポジトリ MCP ツール (`list_components`、`get_component_usage`、`lsp_find_symbol`、および `lsp_list_symbols`) とファイル システム検査を使用して既存のアセットを検査します。
- 重複した UI プリミティブを作成する代わりに `@mission-platform/components` を再利用し、ハードコーディングされたビジュアル値の代わりに `--mp-*` トークンを参照し、共有ユーティリティの `packages/` を検索し、ユーザー向け文字列に `@mission-platform/i18n` を含む YAML カタログを使用します。
- 新しい共有 UI コンポーネント、コンポーザブル、ユーティリティ、およびデザイン トークンは `packages/` に属します。共有 lint、フォーマット、ビルド ツールは `packages/tooling/configs/` に属します。
- パッケージコンポーネントを変更するときは、同じ場所にある `.stories.tsx` ストーリーを追加または更新します。 `apps/storybook` ワークベンチは、Vue、React、Solid、Svelte、および Web コンポーネントにわたるパッケージ ストーリーを検出します。

## 安全なコーディングとコンプライアンス

すべてのコードと構成は ISO/IEC 27001:2022 Control A.8.28 に準拠し、OWASP Top 10 (2025) および CWE Top 25 から保護する必要があります。

- 資格情報、秘密キー、クラウド トークン、その他の秘密を決してコミットしないでください。
- `DOMPurify.sanitize` で HTML をサニタイズし、クエリをパラメータ化し、補間されたシェル文字列ではなく `execFile` などのベクトル引数を使用します。
- SHA-256 や `crypto.getRandomValues` などの最新の暗号化を使用します。セキュリティが重要な値には `Math.random()` を決して使用しないでください。
- 未調査の `postinstall` ライフサイクル スクリプトを回避し、カタログ参照を通じて依存関係を固定します。
- 最小権限、リポジトリのルートとパスの境界、シェルフリーの実行、明示的な書き込み承認、およびセキュリティ ツールの境界を保持します。
- PR を提案する前に、関連する開発者 MCP セキュリティ チェック (該当する場合、`security_scan_secrets`、`security_analyze_code`、`security_audit_dependencies`、`security_audit_supply_chain`、`security_collect_compliance_evidence`、および `security_audit_compliance`) を実行します。

## ワークツリーとビルドの依存関係

- 並列ワークストリームは、`node --experimental-strip-types scripts/worktree-manager.ts create <branch>` でプロビジョニングされた分離された Git ワークツリーを使用する必要があります。
- 新しいワークツリーでは、内部 `dist/` アーティファクトが欠落している可能性があるため、パッケージのテストまたは型チェックの前に上流のワークスペースの依存関係を構築します。

  ```bash
  pnpm exec turbo run build --filter <package-name>^...
  ```

- ワークツリーは `.turbo/cache` を共有します。そのキャッシュを消去したりバイパスしたりしないでください。

## ポータブル LSP 構成

- `agent-lsp.json` の LSP 定義では、`["pnpm", "exec", "<server>", "--stdio"]` や `["pnpm", "--dir", "relative/path", ...]` などの移植可能な相対呼び出しを使用する必要があります。
- 絶対システム パスをハードコーディングしないでください。 MCP LSP サーバーは、検出されたリポジトリまたはワークツリー ルートから言語サーバーを実行します。
- LSP クエリおよび実行ツールにはアクティブなセッションが必要です。 `lsp_status` を確認し、必要に応じて `lsp_start` を使用します。
- TypeScript 7 ネイティブ サーバーは `tsc --lsp --stdio` (`typescript-go` 7.0.2) を使用します。ワークスペース全体のシンボルおよびホバー クエリは、インデックス作成中にタイムアウトになる場合があります。 15,000 ～ 30,000 ミリ秒のプロトコル タイムアウトを使用し、パッケージ スコープのタイプチェックと Vitest でそれらを補完します。
- 起動または検出がタイムアウトした場合は、タスクをブロックするのではなく、パッケージ スコープのタイプチェックと Vitest を診断フォールバックとして使用します。

## フリントとスキャナーの検証

- Flint LSP 診断はソースレベルのフィードバックのみです。これらは、リンクされたマルチモジュール グラフが有効な Wasm を発行すること、またはそのランタイム ABI が正しく実行されることを証明するものではありません。
- スキャナ グラフを変更するには、フォーカスされたグラフ スイート、パッケージ `type-check` およびパッケージ Vitest スイートを実行します。アーティファクト放出エラーをソース診断とは別に記録します。
- フィクスチャまたは削減されたデコーダ パスは、完全な ZXing パリティを確立しません。プランとプル リクエストで、サポートされていないモード、フォーマット サブセット、メタデータ、再試行、およびパブリック コントラクトの移行を明示的にマークします。
- 静的リンクが失敗した場合は、アルゴリズム コードを変更したりテストを弱める前に、グラフ モジュールとエッジの数、エミッター診断、および最小の分離された再生器をキャプチャします。

## コードスタイルと検証

- 新しいソース ファイルは、`.ts` または `.vue` と `<script setup lang="ts">` を使用します。パブリック API とエクスポートされた関数には明示的な型が必要です。
- 外部プロトコルで `null` が必要な場合を除き、値が存在しない、またはクリアされた値には `undefined` を使用します。
- Forge JSX イベント プロパティは、`onKeyDown`、`onPointerDown`、`onMouseDown` などの標準のキャメルケース名を使用します。
- Node 組み込み、外部依存関係、内部 `@mission-platform/*` パッケージ、および相対ファイルのグループ内に空白行を含まない順序でインポートをグループ化します。グループは 1 行の空白行で区切ります。
- `pnpm --filter <pkg> run lint` および `pnpm --filter <pkg> run lint:style` を実行します。該当するスタイル エラーに対してのみパッケージ ESLint 修正を使用してください。マークダウンとストーリーはリポジトリ形式のワークフローを使用します。
- コンパイラー、トランスパイラー、AST、およびコード生成の変更には、エンドツーエンドの統合をカバーする必要があります。同一のベース名に対する非衝突出力、明確なエントリの再エクスポート、および出力された内容の保持を検証します。
- `@mission-platform/forge-plugin-api` では `TargetIntentions.lowered` は必須です。ターゲット プラグインには低プランが必要です。フィクスチャ、モック、および CMS 統合プラグインは、`{ framework, appliedOptimizations: [] }` を提供するか、`lower -> optimize -> generate` を実行する必要があります。
- 並列負荷では、マルチフレームワーク、ドキュメント抽出、および大規模な AST テストでは、明示的な `60_000` ～ `120_000` ミリ秒のタイムアウトを使用する必要があります。
- 横断的な計画作業では、エンドツーエンドの動作、ネガティブ テスト、およびパッケージを対象とした lint ゲートに焦点を当てた独立したレビューを使用します。

## インタラクションモード

最初に適用可能なモードを使用し、永続化ルールで切り替えが許可されない限り、それをセッションの間保持します。

1. 挨拶、雑談、事実に関する質問、または簡単な計算には `[CHAT]`。
2. 読み取り専用の説明、分析、情報検索、または提案用の `[ADVANCED_CHAT]`。
3. `[RUN_VERIFY]`: 短い安全なコマンド、アプリの実行、編集なしのテスト。
4. `[FAST_CODE]` は、追加のコンテキスト収集を必要としない簡単な 1 つのファイルの変更です。
5. ビルド、インストール、インフラストラクチャ、環境修正、またはシステム チェック用の `[SETUP]`。
6. 調査または複数の手順を必要とする重要なプロジェクト変更の場合は `[CODE]`。
7. `[NICHE]` は、別のモードに適合しない特殊なフォレンジック、リバース エンジニアリング、データ回復、またはセキュリティ研究のみに使用されます。

`[CHAT]` と `[CODE]` はモードを切り替えません。 `[ADVANCED_CHAT]` は、明示的な実装要求の後にのみ `[CODE]` に切り替わります。 `[FAST_CODE]` と `[RUN_VERIFY]` が 3 ステップ以内に完了できない場合は、`[CODE]` に切り替わります。 `[SETUP]` および `[NICHE]` は、実装が必要になった場合、`[CODE]` に切り替わる可能性があります。

## アトミック生成とファイル管理

- 生成が成功する前に、生成ターゲットをワイプまたは削除しないでください。 `.forge-attempt/` などの兄弟試行ディレクトリにアーティファクトをステージングし、コミット前診断を実行し、チェックに合格した後にのみアトミック スワップします。
- `.gitkeep` や `.gitignore` などのリポジトリ ドットファイルを保存し、ビルド ターゲットを同期またはプルーニングするときに実行中のステージング ディレクトリを保存します。
- 突然変異を明示的かつ限定的に保ちます。広範囲のクリーンアップ コマンドを使用したり、現在のタスク用に作成されていないファイルを削除したりしないでください。

## 開発者 MCP LSP ワークフロー契約

コード タスクの手動テキスト検索よりも、開発者 MCP の限定された `lsp_*` コード インテリジェンス ツールを優先します。 `lsp_capabilities` を使用して、現在の契約と可用性を確認します。編集する前は読み取り専用の `lsp_review_structure` または `lsp_debug_context` を使用し、LSP 編集を適用する前は `lsp_preview_edit` を使用し、変更後は `lsp_get_diagnostics` を使用し、該当する場合は `lsp_run_build` および `lsp_run_tests` を使用します。

専用のマッピングを使用します。構造には `lsp_list_symbols`、シンボルには `lsp_find_symbol`、使用法には `lsp_find_references`、理解には `lsp_inspect_symbol`、呼び出しサイトには `lsp_find_callers`、関数の置換には `lsp_replace_symbol_body`、未使用のシンボルには `lsp_safe_delete_symbol` を使用します。アーキテクチャ、影響、リファクタリング、安全な編集、テストの関連付け、完全な検証には、文書化された `/lsp-*` ワークフローを使用します。
