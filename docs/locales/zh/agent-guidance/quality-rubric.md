在实施之前使用此标题来选择方法，并在审查期间使用此标题来评估结果。应用适合任务的每个维度；仅文档更改仍然需要简单、可维护、可读且卫生。记录实质性权衡的具体证据，而不是将评分标准视为主观评分。

## 最小的安全变化

- 说明所要求的结果以及可以满足该结果的最小更改。
- 与新的抽象相比，更喜欢现有的存储库模式、包、工具、配置文件和文档。
- 将不相关的清理、推测性重新设计和未经批准的 MCP 运行时更改排除在任务之外。
- 仅当证据表明较小的方法无法保持正确性、安全性或所需的验证时才扩大范围。

## 七个维度

### 简单

- 该解决方案是否使用最少的文件、移动部件、依赖项、状态转换和工具调用来满足要求？
- 它是否重用现有组件、实用程序、令牌、翻译、工作流程或 MCP 功能，而不是重复？
- 推测性抽象、重复的 MCP 工具和不必要的配置更改是否已被删除？

### 复杂

- 识别新的依赖关系、状态、控制流、跨包边缘、配置文件/工具表面、操作步骤和故障模式。
- 解释为什么需要每个不可避免的复杂性来源以及为什么更简单的替代方案是不够的。
- 保持所属包或主题文档的本地复杂性，并避免跨重复源传播策略。

### 可靠性

- 定义可观察的预期行为以及证明该行为的证据。
- 更喜欢确定性行为、有界操作、显式故障处理和安全回退。
- 验证重要的路径，包括负面案例和集成边界；不要将部分固定装置、源诊断或隔离单元视为端到端行为的证明。
- 报告失败、不确定性和未经验证的假设，而不是默默地推断成功。

### 可维护性

- 遵循存储库的结构、命名、依赖关系、测试、文档和所有权约定。
- 将责任放在本地，并为每条规则提供一份规范文档。
- 记录持久的决策和不明显的约束，未来的代理会发现它们。
- 避免陈旧的链接、重复的清单、并行实施以及可能偏离事实来源的措辞。

### 安全

- 保留最小权限、存储库根和路径边界、无 shell 执行、显式突变批准和秘密卫生。
- 防御注入，使用经批准的加密技术和依赖实践，并保留依赖方向。
- 不要为了方便而削弱现有的安全扫描或用更广泛的访问取代有界/只读检查。
- 对于适用的更改，运行相关的开发人员 MCP 安全检查：`security_scan_secrets`、`security_analyze_code`、`security_audit_dependencies`、`security_audit_supply_chain`、`security_collect_compliance_evidence` 和 `security_audit_compliance`。

### 卫生

- 保持差异焦点并保留存储库格式、命名和工作流程约定。
- 删除任务期间创建的临时工件，而不删除预先存在的或会话管理的文件。
- 更新受影响的文档和链接，并验证是否包含生成的、本地的、秘密的或不相关的文件。
- 报告执行的确切验证以及任何无法运行的检查。

### 可读性和理解性

- 使用清晰的标题层次结构、简短的部分、一致的术语和直接的句子，以便目标代理可以快速浏览指南。
- 最大限度地减少认知负担：在采取行动之前提出先决条件，将相关规则放在一起，识别强制性工作与可选工作，并避免无法解释的交叉引用。
- 解释非明显的约束、所有权、优先级、安全边界以及不寻常验证要求的原因。
- 检查链接、示例、名称和输出描述在没有隐藏会话上下文的情况下是否易于理解。
- 执行独立的理解过程：另一个智能体能否遵循指导并仅从文档中选择正确的下一步操作？

## 审核记录

对于一项重要的任务，请在最终审查或移交中总结标题结果。提及最小的安全方法、材料复杂性、可靠性证据、安全和卫生检查以及任何应成为单独授权的后续工作的可读性问题。
