# أفضل ممارسات منصة المهمة

ترجمة آلية مساعدة من المصدر الإنجليزي الأساسي. تُراجع يدويًا عند الحاجة. تبقى أسماء الحزم والأوامر والمسارات والمعرّفات التقنية دون تغيير.

> docs/best-practices.md: [docs/best-practices.md](../../best-practices.md)
> اللغة: العربية (ar)

توضح هذه الوثيقة المبادئ الأساسية والبنية ومعايير الترميز الخاصة بـ Mission Platform monorepo. ذلك
بمثابة **شرح** لسبب اتباعنا لأنماط معينة و**مبدأ توجيهي** للتطوير اليومي.

## المبادئ الأساسية

### العمارة المركبة

تتبع Mission Platform بنية قابلة للتركيب تعتمد على الحزمة. كتل بناء قابلة لإعادة الاستخدام (مكونات واجهة المستخدم،
Composables, Utilities) موجودة في `packages/`، بينما يتم تجميع التطبيقات القابلة للنشر من هذه الكتل في `apps/`.

### الانضباط التبعية

للحفاظ على monorepo قابل للصيانة، فإننا نفرض تدفقًا صارمًا للتبعية في اتجاه واحد:

- **`apps`** → **`packages`**
- **`packages`** → حزم النطاق ذات المستوى الأدنى مثل **`core`**، **`tooling`**، و **`compiler`**

**القاعدة:** يجب ألا يتم استيراد الكود الموجود في `packages/` **مطلقًا** من `apps/`. وهذا يمنع التبعيات الدائرية ويضمن
تظل الحزم قابلة لإعادة الاستخدام حقًا.

### القصص المصورة كطاولة عمل

عند إضافة مكونات أو تعديلها في `packages/`، استخدم تطبيق Storybook (`apps/storybook`) باعتباره التطوير الأساسي لديك
بيئة. لا يحتوي تطبيق `apps/storybook` على القصص نفسها - فهو عبارة عن طاولة العمل المجمعة التي
يكتشف ويعرض القصص التي تعيش جنبًا إلى جنب مع مكوناتها.

- شارك في تحديد موقع كل ملف `.stories.tsx` مع مكونه داخل دليل الحزمة الخاص بهذا المكون (على سبيل المثال.
  `packages/ui/components/src/components/**/<component>/<component>.stories.tsx`)، وليس ضمن `apps/storybook`. هذا يتطابق
  الاتفاقية في [تصميم المكونات الذرية](atomic-component-design.md).
- التحقق من سلوك المكونات عبر Vue وReact وSvelte وSolid وWeb Components عن طريق تبديل
  `STORYBOOK_FRAMEWORK` متغير البيئة. يجب أن يستهلك كل وضع نفس مخزون القصة المحايدة؛ مفقود
  قطعة أثرية الإطار هي فشل في الحزمة/التصدير، وليس سببًا لتصفية تلك القصة.

حلقة التحقق الثابتة الكاملة هي:

```bash
for framework in vue react svelte solid web-component; do
  STORYBOOK_FRAMEWORK="$framework" pnpm --filter @mission-platform/storybook run build-storybook
done
```

## معايير التنمية

### TypeScript في كل مكان

يجب كتابة كافة التعليمات البرمجية المصدر الجديدة في TypeScript (`.ts`) أو Vue SFCs مع `<script setup lang="ts">`.

- **الوضع الصارم**: يتم فرض `strict: true` على جميع ملفات `tsconfig.json`.
- **الأنواع الصريحة**: توفير أنواع صريحة لجميع واجهات برمجة التطبيقات العامة والوظائف المصدرة والمواد القابلة للتركيب.
- **تجنب `any`**: استخدم أنواعًا محددة أو أسماء عامة. إذا كان النوع غير معروف حقًا، فاستخدم `unknown` وقم بتضييق النوع.

### مكونات محايدة للإطار

كلما أمكن، قم بتأليف مكونات واجهة المستخدم باستخدام لهجة `@mission-platform/forge-jsx`. وهذا يسمح للمكونات أن تكون
تم تجميعها واستخدامها في Vue وReact وSvelte وSolid وWeb Components دون إعادة كتابة المنطق الأساسي. تكوين
محلل المستهلك مع حالة `mp:vue` أو `mp:react` أو `mp:svelte` أو `mp:solid` أو `mp:web-component`.

### أنماط التفاعل (Vue 3)

- استخدم **Composition API** حصريًا.
- قم بتفضيل `ref()` لمعظم الحالات للحفاظ على الاتساق.
- قم باستخراج منطق الحالة المعقد إلى **المركبات** (`useXxx`).
- تأكد من تنظيف جميع الآثار الجانبية (المراقبون والفواصل الزمنية ومستمعي الأحداث) بشكل صحيح في `onUnmounted`.

## سير عمل مونوريبو

### عزل المخاوف

- **مكونات واجهة المستخدم الجديدة**: تنتمي إلى `packages/`.
- **الأدوات المساعدة المشتركة**: تنتمي إلى `packages/`.
- **أدوات الوبر/التنسيق/الإنشاء**: تنتمي التكوينات المشتركة إلى `packages/tooling/configs/`.

### التصفية والتنسيق

يتم فرض نمط التعليمات البرمجية المتسق عبر ESLint وPrettier.

- قم بتشغيل `pnpm lint` للتحقق من الانتهاكات.
- قم بتشغيل `pnpm format:write` لإصلاح مشكلات التنسيق تلقائيًا.
- يجب أن تتبع رسائل الالتزام مواصفات **الالتزامات التقليدية**.

### تحضير التبعية الأولية واختبار الحزمة

في monorepo المعياري، تستورد الحزم النهائية بشكل متكرر مخرجات البناء (`dist/`) من الحزم الأولية. للتخلص من حالات فشل اختبار الحالة النظيفة وتجنب تتبع أمر إنشاء الحزم المتعددة يدويًا:

1. **التحضير الآلي للبناء الأولي (`^build`)**:
   تحدد الرسوم البيانية للمهام `turbo.json` `test` و`build:check` ومهام التحقق باستخدام `"dependsOn": ["^build"]`. يؤدي تشغيل أي اختبار أو مهمة فحص الكتابة عبر Turborepo تلقائيًا إلى إنشاء جميع تبعيات مساحة العمل الأولية أولاً.

2. **التنفيذ على نطاق الحزمة**:
   لاختبار أو إنشاء حزمة فردية دون تجميع المتطلبات الأساسية يدويًا:
   - إجراء الاختبارات مع التحضير:
     ```bash
     pnpm test:package <package-name>
     ```
     أو مباشرة عبر Turborepo:
     ```bash
     pnpm exec turbo run test --filter <package-name>
     ```
   - بناء حزمة مع تبعياتها:
     ```bash
     pnpm build:package <package-name>
     ```
     أو مباشرة عبر Turborepo:
     ```bash
     pnpm exec turbo run build --filter <package-name>
     ```

   في مرشحات Turbo، يحدد `<package-name>...` الحزمة ومنبعها
   تبعيات، `...<package-name>` يحدد الحزمة والمصب الخاص بها
   التابعين، ويقوم `<package-name>^...` بتحديد الحزمة الأولية فقط
   التبعيات (باستثناء الحزمة نفسها). يتم تشغيل مساعدي الحزمة بشكل صريح
   النموذج الأولي (`<package-name>^...`) يقوم أولاً بتوجيه سير عمل الحزمة
   احصل على عملية إحماء يمكن التنبؤ بها وقابلة للتخزين المؤقت؛ تبعية `^build` للرسم البياني للمهمة
   تظل شبكة الأمان لاستدعاءات Turborepo المباشرة.

3. **توفير شجرة العمل**:
   عند توفير أشجار عمل Git الجديدة عبر `pnpm worktree:create` أو تهيئتها عبر `pnpm worktree:setup`، يتم إعداد التبعيات الأولية تلقائيًا قبل تشغيل فحوصات التحقق من الصحة، مما يضمن تشغيل أشجار العمل المنشأة حديثًا على الفور.

## تحسين الأداء

- **تقسيم التعليمات البرمجية**: استخدم `import()` الديناميكي للميزات غير المهمة والمكتبات الكبيرة.
- **تحسين الأصول**: تفضيل تنسيقات الصور الحديثة (WebP/AVIF) والتأكد من ضغط جميع الأصول الثابتة.
- **التفاعل الزائد**: استخدم `shallowRef` للكائنات الكبيرة التي لا تتطلب تفاعلًا عميقًا.

## الاختبار والتوثيق

- **التطوير القائم على الاختبار**: يجب أن تكون كل ميزة جديدة أو إصلاح للأخطاء مصحوبًا باختبارات الوحدة (`.spec.ts`).
- **وثائق Diátaxis**: وثائق المؤلف التي تتبع إطار عمل Diátaxis (برامج تعليمية، إرشادية، مرجع،
  شرح).
- **TSDoc**: استخدم TSDoc/JSDoc لجميع الأساليب والخصائص العامة لتعزيز ذكاء IDE.
